# Meminno — Architecture

Living record of what's actually built, as of the issue #24 maxDuration fix (2026-08-07), following the MEM-002 RLS parent-ownership hardening (issue #23) merge earlier the same day. Read `CLAUDE.md` first (operating guide, hard stops, ticket priority), then this. There is no `PRD.md` yet.

## Stack

Next.js 16 (App Router, TypeScript, Turbopack) · Drizzle ORM (`drizzle-orm` + `postgres.js`) · Supabase (Postgres + Auth) · `unpdf` (PDF text extraction, MEM-004) · Upstash Redis (rate limiting + AI budget caps, shared with Propinno under a `meminno-` key prefix) · Stripe (MEM-011: recurring-subscription checkout + webhook, LIVE MODE — see below) · OpenAI (MEM-005 notes generation, MEM-006 flashcards generation, MEM-007 quiz generation, all shipped fail-closed on `OPENAI_API_KEY` — **`OPENAI_API_KEY` was provisioned in Vercel Production and Preview during MEM-008** (2026-08-07), confirmed working via a real production smoke test and via that ticket's own live E2E pass, see "Core UI (MEM-008)" below for the real generate-notes → generate-flashcards → generate-quiz → take-quiz pass this unblocked — going live is also what surfaced MEM-007-fix/issue #26's quiz-generation reliability bug, see that section below) · Vercel · GitHub Actions CI.

## Auth (`lib/session.ts`, MEM-003)

**Flow: magic link (passwordless email OTP), not email/password.** No password field means no reset flow and no password storage/breach surface, and "click one link" is the lowest-friction option for a college-student audience signing up between classes. Uses Supabase Auth's PKCE flow (the `@supabase/ssr` default) rather than the older implicit flow.

- `app/sign-in/page.tsx` — client component. Collects an email, calls `supabase.auth.signInWithOtp({ email, options: { emailRedirectTo: '<origin>/auth/callback' } })` via `lib/supabase/client.ts`. On a brand-new email this sends Supabase's "Confirm your email" signup template; on a returning email it sends the magic-link template — both resolve through the same callback route.
- `app/auth/callback/route.ts` — the `emailRedirectTo` target. Exchanges the `?code=` PKCE param for a session (`supabase.auth.exchangeCodeForSession`, using the code verifier `signInWithOtp` stored in a cookie on the same browser), then calls `getSessionUser()` (which also creates the `public.users` row - see below) before redirecting to `next` (default `/`). Redirects to `/sign-in?error=auth` on any failure.
- `proxy.ts` (Next.js 16's renamed `middleware.ts` convention - see https://nextjs.org/docs/messages/middleware-to-proxy) — refreshes the Supabase session cookie on every request via `supabase.auth.getUser()`. Required because Server Components can read but not write cookies; without this, a token nearing expiry would stay stale until something else happened to set cookies.
- `lib/session.ts` — `getSessionUser()`, the session-gate helper this ticket's brief asked for, mirroring Propinno's `lib/session.ts` discriminated-union pattern (`{ok:true,userId}|{ok:false,status:401|403}`) adapted from Propinno's phone/cookie check to Supabase Auth. Uses `supabase.auth.getUser()` (validates the token against Supabase Auth's server), never `getSession()` (decodes an unverified cookie). **403 is reserved, not currently reachable** — Propinno's 403 means "real session, not an active paying subscriber"; Meminno has no such concept yet (billing is a later ticket). Kept in the type now so callers already handle it.
- `app/api/me/route.ts` — the first real protected route. `GET` returns the caller's own `{id, email, plan}` row (via `withUserContext`) or 401; `DELETE` signs out (`supabase.auth.signOut()`) or 401. Doubles as this ticket's concrete verification target for "does a protected route really 401 when unauthenticated."

### `public.users` row creation — the `auth.users` ↔ `public.users` link is application-level, not a DB FK

Per `lib/db/schema.ts`'s header comment (MEM-002), `public.users.id` matches `auth.users.id` **by convention only** — no DB-level FK is possible (`meminno_app` can never get `REFERENCES` on `auth.users`, the same `auth`-schema platform wall as everywhere else in this codebase). `getSessionUser()`'s private `ensureUserRow(userId, email)` is what upholds that invariant: on **every** successful session resolution (not just a one-time signup step), it runs `withUserContext(userId, tx => tx.insert(users).values({id: userId, email}).onConflictDoNothing())`. Idempotent by design — a second concurrent call for the same brand-new account (e.g. two tabs completing the callback at once) races safely instead of throwing a duplicate-key error. The insert's `withCheck` (`meminno_current_user_id() = id`) only passes because `withUserContext` sets the transaction's identity GUC to the same id being inserted.

### RLS design summary (full reasoning lives in `schema.ts`'s header comment and `CLAUDE.md`)

**Two database roles, and the split is the security control (MEM-002-fix, issue #14).**

| | `meminno_app` | `meminno_rls` |
|---|---|---|
| Env var | `MIGRATION_DATABASE_URL` | `DATABASE_URL` |
| Used by | `drizzle-kit` only | the app (`lib/db/index.ts`) + Vercel |
| Owns | every table + the `drizzle` schema | nothing |
| `rolbypassrls` | false | false |
| In any RLS policy | no, deliberately | yes, with `authenticated` |
| Can read user rows | no (FORCE RLS, no policy) | only the caller's own |

- Every user table is `ENABLE` **and** `FORCE ROW LEVEL SECURITY`, so the owner is subject to its own policies too. `meminno_app` can run DDL but cannot read or write a row of user data. `health_checks` and `drizzle.__drizzle_migrations` are deliberately not FORCEd (no user data; drizzle-kit needs its own tracking table).
- Every policy is `FOR ALL TO authenticated, meminno_rls`, scoped by the caller's own id. No policy for `anon` and no grant to it either — default-deny twice over.
- Policies call `public.meminno_current_user_id()`, created by migration `0002`. It reads the same session GUCs `auth.uid()` reads (`request.jwt.claim.sub` / `request.jwt.claims` for PostgREST, then `app.current_user_id` for the app's own role) with **zero `auth.*` references** — necessary because neither `meminno_app` nor `meminno_rls` can ever be granted `USAGE` on Supabase's managed `auth` schema (grants into it silently no-op; see `CLAUDE.md`). It supersedes MEM-002's `public.rls_current_user_id()`, a `SECURITY INVOKER` wrapper over `auth.uid()` that only `authenticated` could evaluate.
- The app sets that identity via `withUserContext(userId, fn)` in `lib/db/index.ts` — a transaction with `set_config('app.current_user_id', …, true)`. Transaction-local, never session-level: Supabase's transaction-mode pooler hands the same backend connection to unrelated requests between transactions, so a session-level `SET` would be a cross-tenant leak. Outside `withUserContext()` the runtime role has no identity and every query returns zero rows — fail closed.
- Both roles need explicit table-level `GRANT`s in the migration SQL (hand-written; drizzle-kit has no GRANT primitive), because tables `meminno_app` creates get zero default privileges for anyone else — Supabase's default-privilege rules are keyed to `postgres`/`supabase_admin` as creator, not custom app roles. Without them you get a blanket "permission denied for table" that looks like a broken policy but is one layer below RLS.

#### Superseded: MEM-002's `BYPASSRLS` design (corrected here, kept on the record)

MEM-002 originally granted `meminno_app` the `BYPASSRLS` role attribute against live production and had the app connect as that same role, arguing it was the same trust boundary as Supabase's `service_role` with isolation enforced in application code. That was wrong: `service_role` is a narrow escape hatch, whereas this made **every** app query bypass RLS, leaving the policies decorative and nothing to catch a forgotten `WHERE user_id = ...` in a future route. It was also an undisclosed, autonomous production security change. `BYPASSRLS` has been reverted (`NOBYPASSRLS`, verified `pg_roles.rolbypassrls = false`) and is now off-limits on this project — see `CLAUDE.md` HARD STOP 7.

### Known deviations from the ticket's suggested shape

- **No DB-level FK from `users.id` to `auth.users.id`.** The textbook Drizzle+Supabase pattern (a `pgSchema('auth').table('users', ...)` reference + `.references()`) was tried first and abandoned: `meminno_app` can't get `REFERENCES` on `auth.users` or `USAGE` on the `auth` schema by any means tried, including the privileged bootstrap channel (same platform wall as above). Consistency between `public.users.id` and `auth.users.id` is an application-level invariant now, not a database-enforced one. A periodic reconciliation job or an Auth webhook is a reasonable future addition if orphaned profile rows (Auth identity deleted, `public.users` row not cleaned up) become a real problem — nothing like that exists yet.
- **`quiz_attempts.score`** is a plain `integer` (0-100 percentage, not enforced via CHECK constraint) rather than something more structured — matches this schema's existing convention of app-level rather than DB-level value validation.

### RLS parent-ownership hardening (issue #23, fixed 2026-08-07)

Every child table's `withCheck` used to be identical to its `using` — a flat `user_id = caller` check, nothing more. That's sufficient for reads (`using` alone already fully scopes SELECT/UPDATE-target/DELETE), but on writes it let a caller set `user_id` to themselves while pointing the row's parent FK at a different user's parent row entirely: `notes.document_id`, `flashcards.note_id`/`quizzes.note_id`, or `quiz_attempts.quiz_id` could all be forged this way, since Postgres enforces FK referential integrity with RLS bypassed by design — a FK reference is never itself a row-level ownership check. Confirmed empirically against the live project (two disposable test users) on all four tables before this fix, per the finding in issue #23 (filed during MEM-007's review).

**Severity, so this isn't overstated:** no data leak — the unchanged `using` clause means the forger still cannot `SELECT` the forged row back, verified both before and after this fix. Not reachable through the app's own API either — every route derives the parent id from an ownership-verified lookup before ever calling `withUserContext`, never from raw client input. It only ever mattered against a raw `meminno_rls` credential directly. Worth closing anyway: it was a weak existence oracle (a FK-violation vs. success response reveals whether a given parent UUID exists at all) and could leave orphan-ish rows the app's own invariants say should be impossible.

**Fix:** `withCheck` on `notes`, `flashcards`, `quizzes`, and `quiz_attempts` now each add an `EXISTS` subquery requiring the immediate parent row to already be visible to (i.e. owned by) the same caller — e.g. `notes_own_rows`'s `withCheck` is now `(select public.meminno_current_user_id()) = user_id AND EXISTS (SELECT 1 FROM public.documents d WHERE d.id = document_id AND d.user_id = (select public.meminno_current_user_id()))`. `using` is deliberately untouched on every table (read-path scoping was never the gap). `documents` and `users` need no equivalent change: `documents`'s own parent is `users`, and `documents.user_id` already *is* the FK to that parent, so its existing flat check already covers ownership; `users` has no parent row at all. Parent-chain mapping: `notes` → `documents` (`document_id`), `flashcards` → `notes` (`note_id`), `quizzes` → `notes` (`note_id`), `quiz_attempts` → `quizzes` (`quiz_id`). Tightening-only per `CLAUDE.md` HARD STOP 7 — no role attribute, `BYPASSRLS`, or `FORCE ROW LEVEL SECURITY` touched.

**Measured cost:** `EXPLAIN ANALYZE` on the added `EXISTS` subquery in isolation (`notes` → `documents`, live project, table at its current small real-world size) showed 0.215ms execution time, satisfied via a sequential scan — expected and correct at this table's current row count, since Postgres' planner prefers a seq scan over an index scan on very small tables; both `documents.id` (primary key) and `documents_user_id_idx`/equivalent indexes on every parent table are already in place for the planner to use as tables grow. Not a meaningful cost added to any real request path.

## Migrations

- `drizzle/0000_mem-001-scaffold.sql` — `health_checks`.
- `drizzle/0001_mem-002-core-schema.sql` — the 6 tables above, RLS policies, `authenticated` grants, and the `drizzle.__drizzle_migrations` RLS fix (see below). Hand-edited after `drizzle-kit generate`: the auto-generated `CREATE TABLE "auth"."users"` statement was deleted (that table already exists on the real project; creating it would fail, and CI stubs its own copy separately — see below), and the GRANT/RLS-fix statements were appended by hand (drizzle-kit has no primitive for either).
- `drizzle/0002_mem-002-fix-forced-rls.sql` — MEM-002-fix (issue #14). Creates `public.meminno_current_user_id()`, repoints all 6 policies at it and adds `meminno_rls` to each, grants `meminno_rls` DML on the 6 user tables, and `FORCE ROW LEVEL SECURITY` on all 6. Only the `ALTER POLICY` block is drizzle-kit-generated; the function, GRANTs, and FORCE statements are hand-written.
- `drizzle/0003_mem-002-rls-parent-ownership.sql` — issue #23, see "RLS parent-ownership hardening" above. `ALTER POLICY` for `notes`/`flashcards`/`quizzes`/`quiz_attempts`, entirely `drizzle-kit generate`-produced this time (no new table, role, or privilege — nothing to hand-write beyond the header comment).
- `drizzle/0004_mem-012-podcasts.sql` — MEM-012 (issue #47), the `podcasts` table. The first **new table** since MEM-002, so the first to be built against `CLAUDE.md`'s full five-piece convention in one migration instead of acquiring the pieces across three. Two of the five are drizzle-kit-generated (`ENABLE ROW LEVEL SECURITY`, `CREATE POLICY ... TO authenticated, meminno_rls`); the other three are hand-appended, because drizzle-kit's pg-core API has no GRANT or FORCE primitive: `GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE "podcasts" TO "authenticated"`, the same `TO "meminno_rls"`, and `ALTER TABLE "podcasts" FORCE ROW LEVEL SECURITY`. `anon` is deliberately granted nothing. No role, role attribute, or existing table's privileges are touched (`CLAUDE.md` HARD STOP 7). See "Podcast schema + RLS" below.
- `drizzle/0005_mem-018-affiliate-referral-tracking.sql` — issue #52, see "Affiliate/referral attribution" below. One line, entirely `drizzle-kit generate`-produced: `ALTER TABLE "users" ADD COLUMN "referred_by_code" text;`. A new nullable column on an existing table needs no GRANT/FORCE/RLS-policy changes — the existing `users_own_row` policy and existing `authenticated`/`meminno_rls` table grants already cover it (RLS is row-level, not column-level). **Numbering note:** this migration was originally generated and applied to the live project as `0004` (its file content, hash `a09bd123…`, and journal `when` timestamp `1786500013259` all predate MEM-012 merging to `main`) — applied for real *before* MEM-012's own `0004_mem-012-podcasts.sql`. When MEM-012 merged with its own independently-generated `0004`, this migration was renumbered to `0005` (filename + `_journal.json` `idx`/`tag` only) to resolve the collision, with its SQL content and original `when` timestamp deliberately left untouched — `drizzle-orm/postgres-js/migrator`'s `readMigrationFiles()` hashes a migration purely from its `.sql` file's byte content (verified by reading `node_modules/drizzle-orm/migrator.js`), so the rename does not change its identity; `PgDialect.migrate()`'s skip check is a single `lastDbMigration.created_at < migration.folderMillis` watermark comparison (not a per-migration hash lookup), so keeping the original, smaller `when` value is what correctly makes `drizzle-kit migrate` recognize this migration as already-applied (folderMillis below the live watermark) rather than attempting to re-run `ALTER TABLE users ADD COLUMN referred_by_code`, which would fail with "column already exists" against production. A fresh `drizzle-kit generate` here would have assigned a new timestamp exceeding that watermark and reintroduced exactly that failure.
- Applied to the live project (`hlaeqvuyapkvixwaqxcs`) via `drizzle-kit migrate` connecting as `meminno_app` (now via `MIGRATION_DATABASE_URL`, per the role split above), per the proven MEM-001 pattern.

### CI (`.github/workflows/ci.yml`)

Runs against an ephemeral `postgres:17` service container. A bootstrap step before `drizzle-kit migrate` stands in for production's one-time privileged bootstrap: it creates all four roles (`authenticated`, `anon`, `meminno_app`, `meminno_rls`), an `auth.users` table, `auth.uid()` (byte-for-byte matching the real definition), the legacy `public.rls_current_user_id()` (kept only so migration `0001` can replay), and `GRANT USAGE ON SCHEMA auth TO authenticated, anon`. None of this lives in a migration file, since those also run against the real project, which already has real versions of all of it.

Since MEM-002-fix, CI **reproduces production's privilege split** rather than running everything as the container superuser: three connection strings, `ADMIN_DATABASE_URL` (bootstrap step only), `MIGRATION_DATABASE_URL` (non-superuser `meminno_app`, what drizzle-kit uses), and `DATABASE_URL` (`meminno_rls`, what the app and tests use). This matters for correctness of the tests themselves — a superuser bypasses RLS unconditionally, so the isolation and `FORCE` assertions would have proven nothing.

### Pre-existing RLS gap fixed in this ticket

`drizzle.__drizzle_migrations` (drizzle-kit's own tracking table) had RLS disabled since MEM-001, alongside `health_checks`. Both are now `ENABLE ROW LEVEL SECURITY` with zero policies — the correct, complete fix for a table with no user data and no legitimate `authenticated`/`anon` consumer (default-deny to everyone; the owner is not `FORCE`d on these two, deliberately — see the RLS design summary). See `CLAUDE.md`'s "RLS gap" section for the corrected finding this replaced (the original MEM-001 wording had the risk backwards).

## Testing

- `tests/unit/schema.test.ts` — static schema-shape assertions (RLS enabled, exactly one `authenticated`-scoped policy per user table, `user_id` denormalization, cascade deletes, `users.id` has no default). No DB connection needed, always runs. Since issue #23: also pins that `withCheck` (not `using`) on `notes`/`flashcards`/`quizzes`/`quiz_attempts` contains an `EXISTS` clause referencing the right parent table/column, so a regression back to the flat `user_id`-only check would fail this suite before ever reaching a real database. **Since MEM-012**: `podcasts` is covered by every one of those cases, plus one pinning its own lifecycle contract (`status` is `NOT NULL DEFAULT 'pending'`; `storage_path`/`duration_seconds`/`error_message` all stay nullable, so a queued row is insertable with nothing but its two FKs).
- `tests/integration/rls.test.ts` — real cross-user RLS enforcement through the app's **actual** runtime role and connection string (`meminno_rls` via `DATABASE_URL`), not a side connection and not a mock. Inserts real rows for two random test users and asserts: a user reads/writes their own rows; the other user gets zero rows on cross-user SELECT, zero rows affected on cross-user UPDATE/DELETE, and a real `row-level security` error on a forged cross-user INSERT; a session with no identity set sees nothing at all; and `meminno_app` (via `MIGRATION_DATABASE_URL`) can read none of it either. Cleans up its own rows via the same policy-scoped path. ## MEM-009 — Weekly shareable stat card (issue #9)

The product differentiator (see `CLAUDE.md`'s "What Meminno is"): a weekly recap of a user's real study activity, downloadable/shareable as an image.

- **`lib/stats.ts`** — `getWeeklyStats(userId)` computes a trailing-7-day `WeeklyStats` object entirely from real rows (`documents`, `flashcards`, `quizzes`, `quiz_attempts`), through `withUserContext()` like every other user-data query in this app. Metrics: documents added, flashcards generated, quiz questions generated (`jsonb_array_length` computed in SQL, not fetched client-side — a malformed/non-array shape is logged loudly and counted as 0 rather than failing silently), quizzes taken, average quiz score with an `up`/`down`/`flat` trend vs. the prior week, and a current day-streak (consecutive **UTC** days with a document or quiz attempt, forgiving "today" not having happened yet if yesterday was active). **Known limitation, documented in code rather than silently shipped:** UTC-day bucketing can undercount a real streak for non-UTC users — a US-Pacific evening study session already falls on the next UTC day — and a hardcoded fixed-offset "fix" would just trade one bias for another with no per-user timezone signal to bucket by yet (MEM-003's `users` table has no timezone column — a reasonable follow-up once one exists). `isEmpty`/`everActive` flags distinguish a brand-new account from an existing one that was just quiet this week, so the empty state can be honest about which it is instead of showing one generic message — or fabricated numbers — for both. **Auth history, for context on why `lib/session.ts` looks the way it does.** This ticket started before MEM-003 ("Auth") had a branch or PR, and its route needed real auth regardless — not a stub — so it built its own `lib/session.ts` against Supabase Auth infra that already existed (`lib/supabase/server.ts`, since MEM-001): `getSessionUser(req)` calling `supabase.auth.getUser(bearerToken?)` (never `getSession()`), with a `Bearer <token>` path since there was no sign-in UI yet to mint a cookie session. **MEM-003 landed independently in the meantime and shipped its own `lib/session.ts`** (see the Auth section above) — real magic-link sign-in, cookie-only, `{ok,userId}` with no `plan`, `onConflictDoNothing()`. Per two independent reviews at merge time, `lib/session.ts` is MEM-003's file going forward; this ticket reconciled its interim version onto MEM-003's base rather than keeping two copies:

- Kept MEM-003's actual auth-check logic unchanged: `supabase.auth.getUser()`, the no-email-on-session fail-closed check, the discriminated-union shape.
- Added back onto that base: an optional `req?: Request` param so `getUser(bearerToken)` still supports the `Bearer <token>` path this ticket's route and live E2E verification need (existing cookie-only call sites — `app/auth/callback`, `app/api/me` — are unaffected, since `req` defaults to `undefined`); `plan` on the `ok:true` result, so this ticket's per-plan upload caps don't need a second query; and re-exported `SessionResult`/`sessionErrorResponse()`, which `/api/documents` depends on.
- Changed `ensureUserRow`'s upsert from `onConflictDoNothing()` to `onConflictDoUpdate()` — flagged independently by two reviews as the better default, since `onConflictDoNothing()` means `email` never re-syncs if it changes in Supabase Auth after the first sign-in.

**PDF text extraction (`lib/pdfExtract.ts`).** Library: `unpdf`, not the more commonly reached-for `pdf-parse`. Reasoning: `unpdf` ships its own serverless-optimized build of Mozilla's PDF.js (worker inlined, browser-only references stripped), so it runs in a Vercel Node.js function with no canvas native dependency and no separate worker file to resolve — designed for exactly this deployment target. Verified against real PDF bytes twice: once via a throwaway node script during development, and again by `tests/unit/pdfExtract.test.ts`, which builds a real (if minimal) single-page PDF byte stream at test time — not a mock of the PDF.js API — and round-trips it through the real library. Also verified via this ticket's live E2E pass (see below): a real multipart PDF upload through the real route produced real non-empty extracted text stored in a real `documents.raw_text` row in the live Supabase project.

**Two-layer (in practice three-check) rate limiting (`lib/uploadLimits.ts`), enforced on `POST /api/documents` per CLAUDE.md HARD STOP 6:**

| Layer | Mechanism | Scope | Limit | Reasoning |
|---|---|---|---|---|
| 1. Burst | `lib/ratelimit.ts`'s `limitRequest()`, unmodified | per user (`meminno-upload-burst:<userId>`) | 10 req / 10s (existing library default) | Catches rapid-fire abuse/misclick spam within seconds. |
| 2. Daily cap | `lib/aiBudget.ts`'s `claimDailyBudget()`, keyed per user | per user, tiered by `users.plan` | **5/day free**, **50/day paid** | This is the actual free-tier cap number CLAUDE.md flagged as TBD ("Pricing... finalized in MEM-004") — see reasoning in `lib/uploadLimits.ts`'s comments: enough for a real study session, not enough to cover a semester for free. | 3. Document creation doesn't call OpenAI directly, but it gates MEM-005+'s AI generation and PDF extraction is itself real, billable serverless compute, so the same reasoning applies. |

All three are unit-tested in `tests/unit/uploadLimits.test.ts` (mocked `lib/ratelimit`/`lib/aiBudget`, asserting call order, exact keys, and short-circuiting) *and* triggered for real during this ticket's live E2E pass against the live Supabase project (see below) — not just configured, actually observed returning 429s with the expected reason strings once exceeded.

**Rate-limit ordering fix (caught in merge review):** the daily-cap/platform-ceiling claim originally ran in the route *before* the request body was parsed/validated at all (as one `enforceUploadLimits(userId, plan)` call covering all three layers), meaning a request that failed simple validation (wrong file type, no `file`/`text` field, oversized file/text) still burned one of a free user's 5 daily uploads on its way to a 400. Fixed by splitting `lib/uploadLimits.ts`'s single function into two: `checkBurstLimit(userId)` (layer 1 only) and `claimUploadBudget(userId, plan)` (layers 2-3 together, since both are real quota claims that should only happen once), so the route can call them at two different points — burst before parsing the body at all (cheap, content-independent), budget only after the body has been parsed and cheaply validated (content type, size, non-empty text) but *before* the expensive step (PDF extraction) and the DB insert. A PDF that passes those cheap checks but then fails extraction (corrupted/password-protected, or no extractable text) still consumes its quota claim — deliberate, not an oversight: real compute was spent on it by that point, which is exactly the cost this budget exists to bound.

**Route: `POST /api/documents`.** Auth-gates via `getSessionUser`, then: burst-checks (`limitRequest`) *before* parsing the body, parses/validates the `file`/`text` field (PDF, `application/pdf` only, capped at 4MB — see below; or pasted text, capped at 200k characters) plus an optional `title`, only *then* claims the daily-cap/platform-ceiling budget (`claimDailyBudget`, ×2) — deliberately split this way, see "Rate-limit ordering fix" below — and finally inserts a real `documents` row via `withUserContext`. Minimal client page at `/upload` (`app/upload/page.tsx`) exists to prove the flow has a real user-facing entry point; MEM-003's `/sign-in` now provides the real cookie session it needs, though there's still no dashboard/document-library UI linking the two together (out of scope — belongs to whatever ticket builds that shell, MEM-008).

**Deliberate scope decisions/known gaps, not overlooked:**
- **`storage_path` is never populated, even for PDFs** — v1 extracts text synchronously at upload time and stores it directly in `raw_text`, the same storage model as pasted text; the original PDF binary is not persisted to Supabase Storage. Avoids standing up a Storage bucket + object-level RLS policies (a meaningfully separate integration) in a ticket scoped to upload + rate limiting. Revisit if a later ticket needs to re-extract from the original file (e.g. an OCR fallback for scanned PDFs) or wants to offer the original file back for download.
- **4MB PDF cap, not the schema's implicit assumption of "whatever fits".** Vercel Functions hard-cap request bodies at 4.5MB platform-wide, non-configurable (`FUNCTION_PAYLOAD_TOO_LARGE` below that — see Vercel's function-limits docs). 4MB leaves headroom for multipart overhead so this route's own error message fires before Vercel's opaque 413 does. Real image-heavy lecture-slide PDFs can exceed this; the real fix is a future direct-to-Supabase-Storage client upload that bypasses the function body entirely, not something built here.
- **No GET/listing endpoint.** Only `POST` — reading a user's own documents belongs to whatever ticket builds the dashboard/library UI.

## AI notes generation (MEM-005, real GitHub issue #5, 2026-08-06)

The first real AI-generation endpoint in this codebase — the concrete case `CLAUDE.md` HARD STOP 6's two-layer rate limiting was written for. Given a `documents` row the caller owns, generates structured study notes via OpenAI forced tool-use and persists them as a `notes` row.

**A real, load-bearing constraint at ship time: `OPENAI_API_KEY` is unset everywhere** (local `.env.local`, Vercel Production, Vercel Preview — confirmed absent in all three before writing any code). Per this ticket's own dispatch, the feature ships complete and correct with `not_configured` as a first-class, tested, fail-closed path rather than working around the missing key — this is the actual code path every real request takes in this environment today, not a rare edge case. See "Live E2E verification" below: it necessarily exercises this fallback path, not a real generation call, and that is expected and correct, not a shortcut.

**`lib/notesGeneration.ts` — `generateNotesFromText(rawText)`.** Architecture mirrored directly from the Propinno sibling project's `lib/nlpCriteria.ts` (this ticket's dispatch named it explicitly as the closest existing precedent in the whole codebase family):
- OpenAI Chat Completions with **forced** tool-use (`tool_choice` pinned to one function, `generate_study_notes`) rather than free-text generation + regex/JSON.parse — the model can only respond in the exact shape asked for.
- The tool-call output is re-validated with zod (`generatedNotesSchema`) before it is ever trusted, persisted, or returned — it's untrusted model output derived from untrusted user-uploaded content, not just type-checked.
- Every failure mode is a typed, non-throwing result (`{success:false, reason, message}`), never an unhandled exception or a silently empty notes object: `not_configured` (`OPENAI_API_KEY` unset), `empty_input` (nothing to generate from — checked before any API call, so it costs nothing), `invalid_response` (no tool call, malformed JSON, or a validation failure), `api_error` (network/API failure). Mirrors `parseCriteriaFromText`'s exact reason taxonomy, adapted (no Sentry call — this repo, unlike Propinno, has no Sentry DSN configured yet per `CLAUDE.md`'s credential-reuse map, so none of this repo's other `lib/` modules call it either; `logger.warn`/`logger.error` is the existing convention here).
- Model: `gpt-4o-mini`, same choice as `nlpCriteria.ts` and for the same reason — structured extraction/synthesis against a forced schema, not open-ended creative writing, so a fast/cheap model is the right fit, especially given the budget cap below is sized assuming a low per-call cost.
- Input is truncated to 60,000 characters (documents can be up to MEM-004's 200k-character cap) before being sent — bounds prompt size/latency/cost predictably at the cost of losing tail content on unusually long documents; a future ticket could chunk-and-merge instead if that tradeoff matters in practice.

**Notes structure chosen** (`generatedNotesSchema` in `lib/notesGeneration.ts`) — a title/summary plus a structured body, not a text passthrough:
```
{
  title: string,               // derived from the material, not generic
  summary: string,              // 2-4 sentence overview
  sections: [{ heading, bullets: string[] }],  // the material's real structure, distilled to study-ready bullets
  keyConcepts: [{ term, definition }],         // a review/quiz-prep glossary
}
```
Reasoning: this is meant to be genuinely useful study material (the product's whole premise per `CLAUDE.md`'s "What Meminno is"), not a summary blob — `sections` gives a skimmable outline matching how a student would actually review before an exam, and `keyConcepts` doubles as prep for MEM-007/008's flashcards/quiz generation, which can reasonably draw on the same field later. `notes.content` (`lib/db/schema.ts`) is a plain `text` column, not `jsonb` — the object above is `JSON.stringify`'d before the INSERT; the POST response deliberately returns the *parsed* object back to the caller (nicer for an immediate consumer than a raw JSON string), so DB storage shape and API response shape are intentionally decoupled. No schema change was needed — `notes.content` already existed from MEM-002.

**`lib/notesLimits.ts` — two-layer rate limiting on `POST /api/documents/[id]/notes`, mirroring `lib/uploadLimits.ts`'s established shape (per dispatch) rather than inventing a new one:**

| Layer | Mechanism | Scope | Limit | Reasoning |
|---|---|---|---|---|
| 1. Burst | `lib/ratelimit.ts`'s `limitRequest()`, key `meminno-notes-burst:<userId>` | per user | 10 req / 10s (library default) | Catches rapid-fire abuse (e.g. a mashed "generate" button) within seconds, before the route even looks up the target document. |
| 2. Daily cap | `lib/aiBudget.ts`'s `claimDailyBudget()`, key `notes-generation:user:<userId>` | per user, tiered by `users.plan` | **5/day free**, **50/day paid** | Matches `FREE_TIER_DAILY_UPLOAD_CAP`/`PAID_TIER_DAILY_UPLOAD_CAP` 1:1 by design — a free user who uses their whole daily upload allowance should be able to generate notes for all of it without hitting a second, tighter wall right after; regenerating notes for the same document also counts (it's a real OpenAI call each time, not a cached read). |
| 3. Platform ceiling | `claimDailyBudget()` again, key `notes-generation` (global) | all users/plans combined | 300/day | Deliberately lower than the upload flow's 500/day: unlike PDF extraction (compute-only), every notes generation is a real, billed OpenAI call — the actual dollar-cost surface HARD STOP 6 exists for. At `gpt-4o-mini` rates a single ~60k-character document plus a structured response is a fraction of a cent, so 300/day is well under $5 worst case — generous headroom over any realistic pre-launch volume while still bounding the blast radius of a bug/retry-storm/abuse pattern, the exact shape of incident that burned $100 in 6 days on Propinno's uncapped RentCast poller. Revisit upward once there's a real active-user count and real per-call cost data to size against. |

Both layers claim/check in `app/api/documents/[id]/notes/route.ts` only *after* the target document is confirmed to exist, belong to the caller, and have non-empty `raw_text` — the same "don't claim quota before the request is known-valid" ordering `lib/uploadLimits.ts` established for MEM-004 (a 404/422 never burns a day's allowance). Unit-tested in `tests/unit/notesLimits.test.ts` (mocked `lib/ratelimit`/`lib/aiBudget`, asserting call order/keys/short-circuiting, mirroring `tests/unit/uploadLimits.test.ts`) *and* triggered for real during this ticket's live E2E pass (see below).

**Route: `POST /api/documents/[id]/notes`.** Order of operations: validate `id` is a UUID (400 otherwise, before touching the session) → `getSessionUser(req)` (401) → burst check (429, before any DB query) → look up the document via `withUserContext`, filtered by both `id` **and** `userId` explicitly (defense in depth alongside the `documents_own_rows` RLS policy, matching `app/api/me/route.ts`'s own convention) → 404 if not found (a nonexistent id and another user's id are indistinguishable by design — no existence leak) → 422 if `raw_text` is empty, without claiming any budget → claim the daily notes budget (429 if exhausted) → `generateNotesFromText()` → on failure, map `reason` to an HTTP status via a `REASON_STATUS` record (`not_configured: 503`, `empty_input: 422`, `invalid_response: 422`, `api_error: 502`), mirroring Propinno's `app/api/onboarding/parse-criteria/route.ts` exactly → on success, `INSERT INTO notes` via `withUserContext` and return `201` with the parsed structured content. Multiple generations per document are allowed (no "regenerate" special case) — each POST creates a new `notes` row and costs a day's quota.

## AI flashcards generation (MEM-006, real GitHub issue #6, 2026-08-07)

**`lib/flashcardsGeneration.ts` — `generateFlashcardsFromNotes(notesContent)`.** Architecture mirrored directly from `lib/notesGeneration.ts`:

Each card is `{front, back}` (`front` max 300 chars — a short prompt/term/question, not a restatement; `back` max 1000 chars — a concise answer), matching `flashcards.front`/`flashcards.back`'s plain-`text` columns with no further shape needed.

**`lib/quizGeneration.ts` — `generateQuizFromContent(notesContent, flashcards?)`.** Architecture mirrored directly from `lib/notesGeneration.ts`/`lib/flashcardsGeneration.ts`:

## MEM-007-fix: quiz generation reliability (real GitHub issue #26, 2026-08-07)

`OPENAI_API_KEY` went live in production earlier the same day this was filed (real generation genuinely works now for notes/flashcards/quiz), which is what exposed this: `POST /api/notes/[id]/quiz` was failing roughly half of real calls with a `422 invalid_response`. Server logs showed the forced-tool-call arguments coming back malformed (a required field missing on one question, a bare string instead of an object on another) — a class of failure that JSON.parse accepts as valid JSON but that violates the tool's own schema, and that `lib/quizGeneration.ts`'s zod validation could only catch after the (billed) call had already happened. No retry existed.

**Fix 1 — OpenAI structured-outputs `strict: true`** on the `generate_quiz` tool definition. This is the real, correct fix at the source: strict mode makes OpenAI enforce the JSON schema server-side via constrained decoding before the response is ever returned, so the "syntactically valid JSON, wrong shape" failure class (missing required field, wrong type) should no longer occur at all. Strict mode requires every schema object to set `additionalProperties: false` and list every property as `required` — already true here, so the only change needed was adding those two `additionalProperties: false` lines plus `strict: true` itself. `lib/notesGeneration.ts` and `lib/flashcardsGeneration.ts` were deliberately left unchanged: live testing (below) found no evidence of the same failure rate on either, and this ticket's scope was explicit about only touching them with real evidence in hand.

**Fix 2 — a single bounded retry on `invalid_response`**, added as defense-in-depth alongside strict mode, not instead of it. `generateQuizFromContent`'s single OpenAI-call-plus-parse-plus-validate body was factored out into a private `attemptGenerateQuiz(client, sourceText)` helper; the public function now calls it up to twice (`MAX_ATTEMPTS = 2`, a `for` loop bounded by that constant, not an open-ended retry loop) and only retries when the failure `reason` is specifically `invalid_response` — not `api_error` (a real network/API failure retrying immediately is unlikely to help), and not `not_configured`/`empty_input` (retrying a request that can never succeed wastes a call). **Rate-limit interaction (HARD STOP 6), checked explicitly**: `app/api/notes/[id]/quiz/route.ts` calls `claimQuizBudget()` exactly once per POST, *before* calling `generateQuizFromContent` — the route has no visibility into how many OpenAI calls happen inside that one function call, so a retry here can never double-claim a day's quota or bypass the budget check. The real, accepted tradeoff: a single POST can now cost up to two real OpenAI calls instead of one, on the (now rare) retry path.

**Live before/after testing against the real OpenAI API** (`gpt-4o-mini`, real `OPENAI_API_KEY`), calling `generateQuizFromContent` directly — the exact function the route calls, so this exercises real generation the same way a real request would, without needing a live notes row/session for every sample. Two isolated git worktrees were used (one pinned to the pre-fix commit `c3eb916`, one with this fix applied) so "before" and "after" runs could never cross-contaminate. 15 distinct topics (biology, history, CS, chemistry, econ, physics, literature, statistics, psychology, linguistics, etc.) were used, not one fixed input, per the review's own instruction that a fixed input could happen to always pass or always fail:
- **Plain notes only (no flashcards), 15 calls before / 15 after**: 15/15 (100%) both before and after — this simpler prompt shape didn't reproduce the reported failure rate at all in this sample, though the "after" run's logs show the retry firing and recovering 2 genuine `invalid_response` results mid-run (both a `correctAnswer`-doesn't-match-an-option case, not a structural one) that would otherwise have surfaced as user-facing failures.
- **Notes + that note's existing flashcards (7-8 cards), matching real production usage of this route more closely** (the route always fetches and attaches a note's flashcards, and heavier/more complex context is exactly the kind of input this class of bug depends on) — run in two rounds of 10 per side (20 calls each) since the first round's 70%/80% split was too small a sample to trust on its own: **before-fix, 5/20 failed (75% success, 25% failure)**; **after-fix, same content, 2/20 failed (90% success, 10% failure)**. A real, measured improvement (failure rate cut by more than half), though it confirms an honest, important finding: **every single `invalid_response` observed across all 40 of these before/after calls was the `correctAnswer`-doesn't-match-one-of-the-4-`options` zod validation failure** (confirmed both from the logged zod `issues` arrays and from every failure's message text reading "Couldn't generate a **valid** quiz..." — the wording unique to that branch, versus "Couldn't generate a quiz..." for a missing tool call or bad JSON), **not the literal missing-field/bare-string structural malformation quoted in the issue.** That specific structural sub-type was not directly reproduced in this testing session (evidently rarer/more input-dependent than the content-mismatch one), but it is the exact failure class `strict: true` is documented and designed to eliminate at the API level — a `correctAnswer` that doesn't textually match any of that question's own options is a cross-field *semantic* constraint, not expressible in JSON Schema's type system, so `strict: true` cannot and does not address it by design; the retry is what recovers from it when it does, though not reliably in this specific heavy-prompt scenario: of the 2 after-fix calls (out of 20) whose first attempt hit `invalid_response`, the retry recovered 0 of them (both failed again on the second attempt too, accounting for the 2/20 final failures) — a genuinely honest result, not the retry "always working." The retry fared better on the lighter plain-notes-only sample above: both of its 2 first-attempt failures were recovered on retry.
- No `api_error`/`not_configured`/`empty_input` results occurred in any of this testing (a real key was configured throughout); every failure observed was `invalid_response`.

**Unit tests updated** (`tests/unit/quizGeneration.test.ts`): a new test asserts the tool definition actually requests `strict: true` with a strict-compliant schema (`additionalProperties: false` at both object levels, all three fields listed in `required`) — a regression here would silently reopen this exact bug. The four existing "fails gracefully on `invalid_response`" tests were updated to queue the same malformed mock response twice (once per attempt) and assert `mockCreate` was called exactly twice, reflecting real retry behavior when both attempts genuinely fail. Two new tests pin the retry's actual value: one asserts a first-attempt failure followed by a second-attempt success returns a successful result (`mockCreate` called twice), and one asserts an `api_error` does *not* retry (`mockCreate` called once) — confirming the retry is scoped to exactly the failure reason it's meant for. `tests/unit/quiz-route.test.ts` needed no changes: it mocks `generateQuizFromContent` wholesale, so the retry (entirely internal to that function) is invisible to it, and it already independently pins that `claimQuizBudget` is called exactly once per request regardless.

**Corroborated independently by MEM-008's own live E2E testing** (see the "Core UI" section immediately below, its "Second live E2E pass" — that ticket hit this exact bug live, in the real UI, while verifying an unrelated feature): its first real "Generate quiz" click against real generated notes returned a real `422` with the message "Couldn't generate a valid quiz from these notes," which that section's own write-up already correctly attributed to `lib/quizGeneration.ts`'s `correctAnswer`-must-match-one-of-4-options `.refine()` — independent confirmation, from a completely different ticket/session/test data, that the `correctAnswer`-content-mismatch sub-type (not the literal missing-field one) is a real, recurring failure mode in production, not an artifact of this ticket's own synthetic test content.

The actual "upload → notes → flashcards → quiz" flow. `getDocumentDetail(userId, documentId)` (`lib/documents.ts`) does the initial server-side fetch (document + its most-recently-created notes row + that note's full flashcard set + every quiz generated from it, each annotated with the caller's own latest attempt score); `DocumentWorkspace` (client component) owns the generate-notes/generate-flashcards/generate-quiz interaction from there, calling the existing `POST /api/documents/[id]/notes`, `POST /api/notes/[id]/flashcards`, `POST /api/notes/[id]/quiz` routes directly (no new routes needed for generation — MEM-005/006/007 already built them, this ticket just finally gives them a caller).

**Why "most recently created notes row," not something more elaborate:** MEM-005/006/007 all deliberately have no "regenerate" special case — every POST creates a fresh row, nothing versions or supersedes anything at the schema level. ### Quiz-taking — `app/dashboard/documents/[id]/quiz/[quizId]/page.tsx` + `components/quiz-runner.tsx` + `POST /api/quizzes/[id]/attempts`

The part MEM-007 explicitly scoped out ("`quiz_attempts` creation, scoring, and any submit-answer flow are NOT built here... actually building it is left to MEM-008" — that ticket's own header comment) and the brief calls out as "the part no prior ticket built."

**`lib/documents.ts`'s `getQuizForTaking(userId, quizId)`** fetches a single quiz scoped to the caller (same cross-user-isolation convention as every other read in this codebase: a nonexistent quiz and another user's quiz both resolve to `null` → the page calls `notFound()`), with its `questions` already validated into a typed shape via `lib/quizAttempts.ts`'s `storedQuestionsSchema` rather than trusted as the schema's untyped `jsonb` column.

**`components/quiz-runner.tsx`** is a real question-by-question UI: one question at a time, 4 selectable options, Back/Next navigation, "Submit quiz" on the last question. Deliberately does **not** compute or display a score client-side before submitting — the only thing it sends the server is the raw list of selected answers; scoring happens entirely server-side (see below), so a client can't forge a better result than what it actually answered. On success, renders a real results screen: overall score, and a per-question breakdown (the caller's answer, correct/incorrect, and the right answer revealed for anything missed).

**`POST /api/quizzes/[id]/attempts`** (`app/api/quizzes/[id]/attempts/route.ts`) — this ticket's one new route, mirroring every sibling AI-generation route's structure (`app/api/notes/[id]/quiz/route.ts` most closely) even though it isn't one:
- Same order of operations: validate `id` is a UUID (400) → `getSessionUser(req)` (401) → burst check (429) → parse/validate the JSON body against `lib/quizAttempts.ts`'s `submitAnswersSchema` (`{answers: string[]}`, 400 on anything else) → look up the quiz via `withUserContext`, filtered by both `id` **and** `userId` explicitly (defense in depth alongside the pre-existing `quizzes_own_rows` RLS policy — no schema change needed, `quiz_attempts` and its `quiz_attempts_own_rows` policy/GRANTs/FORCE RLS all already existed from MEM-002/MEM-002-fix) → 404 if not found, indistinguishable from another user's quiz id by design → validate the stored `questions` shape (500, not 400, if malformed — should be unreachable for anything MEM-007's generator produced, matches `app/api/me/route.ts`'s "should be unreachable" convention for a similarly-impossible state) → 400 if the submitted answer count doesn't match the question count → score (`lib/quizAttempts.ts`'s `scoreQuizAttempt`, a pure function: exact-string match per question against `correctAnswer`, `score` rounded to a 0-100 integer percentage) → `INSERT INTO quiz_attempts` via `withUserContext` → `201` with the persisted row plus a full per-question `results` breakdown for the UI.

## maxDuration + client-side OpenAI timeout on AI-generation routes (real GitHub issue #24, 2026-08-07)

`OPENAI_API_KEY` went live in Production during MEM-008 (2026-08-07), which meant all three AI-generation routes (`app/api/documents/[id]/notes/route.ts`, `app/api/notes/[id]/flashcards/route.ts`, `app/api/notes/[id]/quiz/route.ts`) were now making real `gpt-4o-mini` calls in production with **no serverless function timeout declared** (`grep -rn "maxDuration\|export const runtime" app/` returned nothing) — every request ran on whatever Vercel's account-level default was, and a hung/slow call would be killed opaquely by the platform instead of returning one of the typed failure reasons these routes carefully handle, after `claimDailyBudget` had already claimed the day's quota (by design — see HARD STOP 6). MEM-007-fix's retry logic (up to 2 attempts on `invalid_response`) made the quiz route's worst case meaningfully longer than the other two, so a single flat number across all three wasn't right.

**What Vercel's actual default turned out to be, checked before picking any numbers (per this ticket's own instruction not to guess):** `npx vercel project inspect meminno` and `vercel inspect <deployment-url>` don't surface Fluid Compute/function-duration settings directly, and the CLI's own credential store isn't something this session reads to call the API directly (a live dashboard login was also not attempted — entering credentials is out of scope for an agent session). What's confirmed instead, from Vercel's own current docs (`vercel.com/docs/functions/configuring-functions/duration`, `last_updated: 2026-07-01`): **Fluid Compute has been the default for all new projects since April 2025**, and under it, Hobby-plan functions get **300s (5 minutes) as both the default and the maximum** (Pro/Enterprise can go higher, up to 800s standard / 1800s in an extended-duration beta). The `meminno` Vercel project was created 2026-08-06 — one day before this ticket — so it almost certainly inherited that default; there is no realistic path by which it would have shipped with Fluid Compute off. Net effect: the actual risk here was **not** "the default is too short" (300s is generous) — it's that the **openai SDK's own default timeout (600,000ms / 10 minutes, retried up to `maxRetries: 2` times per the SDK's own doc comment: *"request timeouts are retried by default, so in a worst-case scenario you may wait much longer than this timeout"*) is longer than even that generous 300s ceiling**. Without a client-side timeout, a genuinely hung OpenAI call would eventually get killed by the platform's actual ceiling rather than ever hitting the SDK's own timeout — the opaque-platform-timeout failure mode this issue describes, regardless of what `maxDuration` ends up set to.

**Fix 1 — explicit `maxDuration` on all three routes**, sized against each module's real worst case rather than left at either the account default or the Fluid Compute ceiling:
- `app/api/documents/[id]/notes/route.ts`, `app/api/notes/[id]/flashcards/route.ts`: **60s**. Single generate call each; worst case is `(OPENAI_MAX_RETRIES + 1) × OPENAI_TIMEOUT_MS` = 2 × 20s = 40s, plus session/DB/Redis overhead (session lookup, burst check, document/notes lookup, budget claim, final insert) — comfortably inside 60s.
- `app/api/notes/[id]/quiz/route.ts`: **120s**. `lib/quizGeneration.ts`'s own `MAX_ATTEMPTS = 2` retry (MEM-007-fix) means worst case is `MAX_ATTEMPTS × (OPENAI_MAX_RETRIES + 1) × OPENAI_TIMEOUT_MS` = 2 × 2 × 20s = 80s, plus this route's own overhead (notes lookup, flashcards lookup, budget claim, insert) — 120s leaves real margin.

All three stay well under the 300s Fluid Compute ceiling described above (verified via `functions-config-manifest.json` in a local production build, which correctly shows `maxDuration: 60, 60, 120` for the three routes) — the point of setting these explicitly isn't that the default was too short, it's (a) not depending on an implicit platform default that can change, and (b) bounding a genuinely stuck function to a small, deliberate fraction of that ceiling instead of the full 5 minutes, the same "bound the blast radius of a bug" reasoning HARD STOP 6 already established for the OpenAI daily budget caps.

**Fix 2 — explicit client-side OpenAI timeout/retry budget**, added to all three generation modules (`lib/notesGeneration.ts`, `lib/flashcardsGeneration.ts`, `lib/quizGeneration.ts`) as `OPENAI_TIMEOUT_MS = 20_000` / `OPENAI_MAX_RETRIES = 1`, passed to `new OpenAI({ apiKey, timeout, maxRetries })`. This is the fix that actually matters regardless of what `maxDuration` ends up being: it's what makes a hung upstream call resolve to the existing typed `api_error` result (already handled, tested, and mapped to a `502` by each route's `REASON_STATUS`) instead of the platform killing the function with no response body at all. `lib/quizGeneration.ts`'s `generateQuizFromContent` already constructed its `OpenAI` client once and reused it across both `MAX_ATTEMPTS` attempts (unchanged by this fix) — the timeout/retry budget therefore applies per attempt, not per `generateQuizFromContent` call, which is what the 2×2×20s worst-case math above assumes. `api_error` results are not retried by `lib/quizGeneration.ts`'s own outer loop (only `invalid_response` is), so a hung call there fails after a single attempt, not two.

**Verification:** `tsc --noEmit`, `npm run lint`, and the full `npm test` (215 passed, 7 skipped — the pre-existing DB-gated integration tests, which skip cleanly with no `DATABASE_URL` set in this worktree, same as every prior ticket's local run) all ran clean, plus a full `npm run build`, whose `functions-config-manifest.json` and compiled route chunks were inspected directly to confirm both fixes actually landed in the build output (not just the source). Each generation module's unit test file (`tests/unit/notesGeneration.test.ts`, `tests/unit/flashcardsGeneration.test.ts`, `tests/unit/quizGeneration.test.ts`) gained two new tests: one asserting `new OpenAI(...)` is actually constructed with `{ timeout: 20_000, maxRetries: 1 }` (via a small extension to the existing class-mock — an outer-scope `constructorCalls` array populated from the mock's constructor, same hoisting-safe pattern as the existing `mockCreate` spy), and one simulating a hung/timed-out OpenAI call (a rejected promise carrying a `name: 'APIConnectionTimeoutError'`-style error) and asserting it degrades to `{ success: false, reason: 'api_error' }` rather than an unhandled rejection — `lib/quizGeneration.ts`'s version additionally asserts this happens after exactly one attempt (`mockCreate` called once), confirming `api_error` genuinely isn't retried. Real generation was exercised too, not just mocked failure paths: since `OPENAI_API_KEY` is live now (per MEM-008), all three routes were driven with real requests via `npm run dev` against the live project and completed normally well inside their new `maxDuration` values, confirming the tighter client-side timeout doesn't false-positive on legitimate (fast, successful) calls.

**Deviation from the ticket prompt worth flagging:** confirming Vercel's *exact* per-project Fluid Compute setting for `meminno` specifically (as opposed to the documented platform-wide default any new project inherits) would have required either the dashboard (login = entering credentials, out of scope for this session) or extracting a raw API token from the Vercel CLI's local credential store, which this session's permission classifier correctly declined as a credential-file read. The conclusion above (Fluid Compute on, 300s Hobby ceiling) is well-sourced from Vercel's own current docs and the project's creation date, not directly read off the project's dashboard settings — noted so a future session doesn't treat it as a verified dashboard reading if that distinction ever matters.

## Stripe billing (MEM-011, real GitHub issue #11, 2026-08-07)

Recurring-subscription checkout + webhook, ported from the Propinno sibling project's `lib/billing.ts` (named directly in this ticket's dispatch as the template). **Unlike every prior AI-generation ticket in this repo, this one is NOT a "key is unset, ship the fail-closed path" situation** — Meminno's Stripe account was created directly via the API before this ticket started (a confirmed Pranav decision to skip test mode entirely, the same way Propinno's own billing is live-mode-only), so `STRIPE_SECRET_KEY`/`STRIPE_PUBLISHABLE_KEY`/`STRIPE_WEBHOOK_SECRET`/`STRIPE_PRICE_MONTHLY`/`STRIPE_PRICE_SEMESTER` are all real, live credentials in both Vercel Production and local `.env.local`. See `CLAUDE.md`'s credential-reuse map for the account/price/webhook-endpoint ids.

**Because this account is live-mode, this ticket never completed a real Stripe Checkout session or caused any card to be charged** — that would be a real financial transaction requiring its own separate go-ahead, explicitly out of scope for this dispatch. See "Verification performed" below for exactly what was and wasn't exercised against the real account.

### Two real deviations from Propinno's `lib/billing.ts`, both forced by Meminno's own architecture, not stylistic choices

1. **No `status`/`accessExpiresAt` columns.** Meminno's `users` table (MEM-002) only has `plan` (`'free' | 'monthly' | 'semester'`), `stripeCustomerId`, `stripeSubscriptionId` — `plan` IS the current entitlement, kept in sync by whichever webhook last fired, not a fixed-length access window to extend/expire. This makes `lib/billing.ts` here simpler than Propinno's: no `planDays`/`subscriptionPeriodEnd` arithmetic, no renewal-extends-an-expiry-date logic. A renewal (`invoice.payment_succeeded`, `billing_reason === 'subscription_cycle'`) exists to self-heal `plan`/`stripeSubscriptionId` and catch stale/superseded events, not to compute a new expiry.

2. **RLS makes Propinno's cross-user webhook-resolution pattern structurally impossible here, and the fix does not touch any role/grant/policy.** Propinno has no RLS (single trusted DB role); its `findUserForSubscription()` runs a plain `WHERE stripe_subscription_id = ...`/`WHERE stripe_customer_id = ...` scan across every user. Every Meminno user table is `FORCE ROW LEVEL SECURITY` with policies scoped to `public.meminno_current_user_id()` (see the "Two-role database architecture" section above) — a query outside `withUserContext(userId, ...)` returns zero rows by design, and there is no service-role-equivalent escape hatch on this project (granting one is off-limits without Pranav's explicit go-ahead, per `CLAUDE.md` HARD STOP 7). A webhook event, though, arrives with a Stripe customer/subscription id, not a Meminno userId — the same chicken-and-egg problem MEM-002's original (reverted) `BYPASSRLS` design existed to work around globally, but scoped down here to one specific, narrow read pattern instead of a blanket escalation.

   The resolution: every checkout session this app creates sets `subscription_data: { metadata: { userId, plan } }` (`app/billing/actions.ts`), so the Stripe Subscription object itself always carries our own userId, for the lifetime of that subscription — Stripe preserves subscription metadata regardless of what our own DB row currently says. `lib/billing.ts` reads userId from that metadata instead of scanning our DB for it: directly off the event payload for `customer.subscription.deleted` (its `data.object` IS the Subscription), and via one `stripe.subscriptions.retrieve()` call for `invoice.payment_succeeded` (Invoices don't carry our metadata, but the subscription they belong to does). `checkout.session.completed` needs no lookup at all — `session.client_reference_id` is the userId directly, same as Propinno. Once userId is known, every DB touch goes through `withUserContext(userId, ...)` like everywhere else in this app. This is arguably more robust than Propinno's DB-lookup fallback (it doesn't depend on our own row already holding the right id), not a downgrade forced by the constraint — but it is a real design change from the template, worth flagging explicitly since the dispatch asked to "mirror Propinno's `lib/billing.ts` state-machine logic closely."

What WAS kept identical to Propinno, because the underlying risks are the same: the stale-event guard (a redelivered/late event for a subscription the user has since replaced must never stomp the current one — verified for real, see below); `cancelStripeSubscription()` being idempotent on an already-gone/already-canceled subscription, rethrowing on any other failure so a caller never records "canceled" when it didn't actually happen; `invoice.payment_succeeded` only treating `billing_reason === 'subscription_cycle'` as a renewal (the exact Propinno lesson this ticket's dispatch named directly — a `subscription_create` invoice is the first invoice of a brand-new subscription, already fully handled by `checkout.session.completed`); and `invoice.paid` deliberately not also being handled (same renewal event as `invoice.payment_succeeded`, subscribing to both would double-process every cycle). **`cancelStripeSubscription()` cancelling IMMEDIATELY (not at period end) was originally also kept identical to Propinno — see "Post-review fix" below for why that was changed post-review to `cancel_at_period_end` instead.**

### No equivalent to Propinno's "I found a place" pattern — a real scope decision, not an oversight

Propinno's `markFoundPlace()` is triggered by a specific product event (a subscriber telling the app they no longer need it because they found an apartment) that automatically cancels billing as a side effect of that product action. Meminno has no analogous concept — no "I'm done studying" moment exists anywhere in this product's schema or UX, and inventing one wasn't this ticket's call to make (per its own dispatch: "if there's no clear equivalent yet, it's fine to skip this specific piece — don't invent product scope that doesn't exist").

What this ticket DID add instead, as a baseline requirement of selling real recurring subscriptions rather than a "found a place"-style feature: a plain, manual **"Cancel subscription"** button (`app/billing/actions.ts`'s `cancelSubscription()`, rendered on `/billing` via `components/billing-plans.tsx`'s `CurrentPlanCard`). A subscriber needs *some* way to stop being billed without emailing support — that's the actual requirement live recurring billing imposes, independent of whether the product has a "goal achieved" moment. **As originally shipped, ordering mirrored `markFoundPlace()` exactly: cancel at Stripe FIRST, write `plan: 'free'`/`stripeSubscriptionId: null` to the DB only after that succeeds. Post-review (see "Post-review fix" below), the DB write on success was removed entirely** — `plan`/`stripeSubscriptionId` now stay untouched by this action, since the fix means the user is still correctly entitled to paid access until Stripe itself fires `customer.subscription.deleted` at the real period end. A failed cancel still leaves the row untouched and is safely retryable either way, since `cancelStripeSubscription()` is idempotent.

### Checkout (`app/billing/actions.ts`)

`createCheckoutSession(plan)` — session-gated (`getSessionUser()`), rate-limited (`limitRequest`, keyed per-user rather than Propinno's per-IP, since a verified Supabase Auth session is available at this layer unlike Propinno's raw-cookie-UUID check), refuses a second checkout for a user who already holds a live subscription (same guard as Propinno — a duplicate purchase would leave two subscriptions against one account with only one cancellable from this page), reuses an existing Stripe customer id on re-subscribe, and creates a `mode: 'subscription'` Checkout Session with `client_reference_id`/`subscription_data.metadata.userId` set as described above. `getBillingStatus()` reads the caller's own `plan`/`stripeSubscriptionId` (via `withUserContext`) for `/billing`'s initial render.

Mirrors Propinno's route almost verbatim: verify `stripe-signature` against `STRIPE_WEBHOOK_SECRET` (`stripe.webhooks.constructEvent`, rejecting on any failure with 400), rate-limited (`meminno-stripe-webhook` — this Upstash instance is shared with Propinno, every key here is `meminno-`-prefixed per `CLAUDE.md`'s credential-reuse map), fan out to `lib/billing.ts`'s `handleStripeWebhookEvent()`, 200 on success / 500 if processing throws. ### Post-review fix: cancellation moved to `cancel_at_period_end`, not immediate

The independent merge-evaluation review of this PR flagged a real consumer-disclosure problem: `cancelStripeSubscription()` originally cancelled **immediately** (a straight port of Propinno's `stripe.subscriptions.cancel()`), and `cancelSubscription()` wrote `plan: 'free'` to the DB right away. Propinno's immediate cancel is correct there because it's triggered by "I found a place" — a user-declared completion event where continuing access serves no purpose. Meminno's "Cancel subscription" button has no such signal; it's a generic account action, so immediate cancellation meant a Semester subscriber ($59.99/4 months) who cancelled on day 5 would forfeit ~115 days of already-paid access with **no refund and no warning** — the UI copy only promised "you won't be billed again," never disclosing the access loss, with no confirmation step.

**Fix:** `cancelStripeSubscription()` (`lib/billing.ts`) now calls `stripe.subscriptions.update(id, { cancel_at_period_end: true })` instead of `.cancel()` — no further charge is ever attempted, but access continues through the end of the period already paid for. `plan`/`stripeSubscriptionId` are deliberately left untouched by `cancelSubscription()` (`app/billing/actions.ts`) at cancel time; they only revert to `'free'`/`null` once Stripe itself fires `customer.subscription.deleted` at the real period end — `handleSubscriptionDeleted` already handled that correctly and needed no changes. `getBillingStatus()` gained a live `stripe.subscriptions.retrieve()` read (only when a `stripeSubscriptionId` exists) to expose `cancelAtPeriodEnd`/`currentPeriodEnd` — this schema has no column for "scheduled to cancel," so the live Stripe read is the source of truth rather than a new migration; a retrieve failure fails closed to "not scheduled," which is the safer default (worst case a stale "renews automatically" copy, never a false "canceled"). One API-version note verified against the installed `stripe` package's own type definitions (not assumed): `current_period_end` no longer lives on `Subscription` root on the `2026-07-29.dahlia` pin — Stripe moved it to `items.data[0].current_period_end` since a subscription can have multiple items with independent billing cycles — hence the new `currentPeriodEndFromSubscription()` helper. `components/billing-plans.tsx` now renders a distinct "cancellation scheduled, access continues through &lt;date&gt;" state instead of jumping straight back to the subscribe cards, and the "still active" copy is now accurate about the no-refund/access-continues consequence rather than silent on it. 10 new/updated tests across `tests/unit/billing.test.ts`/`tests/unit/billing-actions.test.ts` cover the new `cancel_at_period_end` call shape, the period-end helper, `getBillingStatus()`'s live Stripe read (including its fail-closed path), and that `cancelSubscription()` genuinely makes zero DB writes on success now.

## Live lecture recording + transcription (real GitHub issue #42, 2026-08-09)

The first ingestion path that isn't a file or a paste: record a lecture live in the browser, transcribe it as it goes, and save the result as a normal `documents` row that flows through the existing notes → flashcards → quiz pipeline untouched. Direct Pranav-requested feature, not pulled from the Phase 2 backlog list verbatim — it was Turbo AI's original core use case, and `app/page.tsx` had advertised it as "on the roadmap" since MEM-010.

### The constraint that dictates the entire design

**Vercel Functions cap request bodies at 4.5MB, platform-wide and unconfigurable** (the same real limit `app/api/documents/route.ts`'s `MAX_PDF_BYTES` comment already documents). OpenAI's transcription endpoint separately caps a file at 25MB. A 50-90 minute lecture at any usable bitrate blows past the *smaller* of those two by a wide margin, so the MEM-004 shape — one upload, one request — would silently cap out somewhere around 15-30 minutes and quietly truncate the thing the user actually cared about. Everything below follows from that: the recording is split client-side into segments that each comfortably fit one request, transcribed one at a time, and only reassembled into a document at the end.

### Why stop/restart, not MediaRecorder's `timeslice`

The obvious approach — `recorder.start(timeslice)` so `ondataavailable` fires periodically — does **not** work here, and this is the single most important thing to know before editing `components/lecture-recorder.tsx`. For one continuous recording session those periodic blobs are not independently decodable: only the first carries the container header, so every later one is undecodable on its own and OpenAI rejects it. Producing genuinely independent, individually-transcribable segments requires actually stopping one `MediaRecorder` (which finalizes a complete, headered blob) and starting a fresh one on the same still-open `getUserMedia` stream. That's what this component does, on an 8-minute cycle. The cost is a real, disclosed gap of tens of milliseconds at each cycle boundary. **This was verified empirically, not assumed** — see the segment-independence result below, which is the direct proof.

### Pieces

- **`lib/audioTranscription.ts`** — `transcribeAudioChunk(file)`, OpenAI `gpt-4o-mini-transcribe` (a real model id, checked against the installed SDK's own type definitions, and the same cost-conscious `-mini` choice every other OpenAI call in this codebase makes). Same typed-result-never-throws contract as `lib/notesGeneration.ts` and friends (`not_configured` / `empty_input` / `invalid_response` / `api_error`), deliberately *without* the forced-tool-use + zod machinery those use — there's no structured shape to force out of a plain audio-to-text call. `OPENAI_TIMEOUT_MS = 60_000`, `OPENAI_MAX_RETRIES = 1`: a transcription call actually processes audio rather than tokens, so it warrants a more generous per-attempt budget than the 20s the chat-completion modules use.
- **`app/api/documents/record-chunk/route.ts`** — stateless, one chunk in, text out, no DB write at all. `maxDuration = 180`, sized against the module's own worst case (2 × 60s) plus session/limit overhead. Enforces its own `MAX_CHUNK_BYTES = 4MB` so an oversized chunk gets a clear message from us rather than an opaque platform 413 — deliberately sized to the *platform* ceiling, not to the ~1.9MB a well-behaved 8-minute segment actually produces, because the point is to catch a browser that ignored the bitrate hint.
- **`lib/recordingLimits.ts`** — the mandatory two layers (HARD STOP 6), but **scoped per chunk rather than per generation**, which is the one genuinely new rate-limit judgment call here. A single real lecture naturally produces roughly 7-12 chunk calls, so charging those against a notes/flashcards/quiz-style 5/day cap would break the feature halfway through a student's first lecture. Caps are therefore sized in chunks: **40/day free, 200/day paid, 1500/day platform-wide**, in its own `recording-transcription` Redis namespace. The platform ceiling is explicitly a conservative starting guess, not measured cost — transcription bills per audio-minute, a different cost shape from the per-token caps `lib/notesLimits.ts` sized its number against, so revisit it once real invoice data exists. There is deliberately **no per-recording-session cap**: the final save goes through `POST /api/documents`, which already claims a per-user daily upload budget, so a session cap would double-gate the same user action for no added protection.
- **`components/lecture-recorder.tsx`** — the client. One continuous `getUserMedia({audio:{channelCount:1}})` stream, 32kbps mono, recorder stopped and restarted every 8 minutes, each finished segment uploaded as it completes while recording continues, transcripts accumulated in order behind a live preview. Hard cap of 90 minutes total (auto-stops and saves rather than truncating silently). A failed segment degrades to a visible `[transcription failed for this segment]` marker and the recording carries on, per the issue's explicit "degrade, don't abort" decision.
- **`app/api/documents/route.ts`** — extended, not rewritten. `parseUpload()` gained a `recordingText` field producing `{kind:'recording'}`, reusing every bit of that route's existing session/burst/budget/RLS/insert path. A separate field from `text` on purpose, so a saved recording is distinguishable rather than masquerading as a paste.
- **No migration.** `documents.sourceType` is a plain `text` column, not a `pgEnum` — exactly so it could grow, as its own MEM-005-era comment anticipated. `'recording'` is the third value. `app/dashboard/page.tsx` and `app/dashboard/documents/[id]/page.tsx` label it "Recorded lecture". No new table, so none of the five RLS obligations apply.

### Five real corrections made during this ticket's own verification

The feature arrived implemented but never once executed. Getting it green and driving it for real turned up five genuine defects, all fixed here rather than shipped:

1. **`npm run lint` failed outright** (`react-hooks/immutability`): `startNewRecorderCycle` referenced itself inside its own `useCallback` body to schedule the next cycle. Fixed by routing the self-restart through a `startCycleRef` assigned in an effect — the recursion is inherent to the design, the direct self-reference was not.
2. **Safari would have failed on every segment.** The upload filename was hardcoded `segment-N.webm` even when the recorder had negotiated `audio/mp4` (the Safari path the component explicitly supports). OpenAI infers audio format from the *filename extension*, so a valid mp4 named `.webm` is rejected as a corrupt webm. Added `extensionForMimeType()` deriving the extension from the blob's real type.
3. **The recorder hung on "Saving…" forever after a successful save**, sitting next to the parent's success message — it never left the `saving` phase. Now returns to idle, which also makes recording a second lecture one click.
4. **All five new route tests failed**, and for a reason worth recording: `vitest.config.ts` sets `environment: 'jsdom'` repo-wide, so `globalThis.File` is jsdom's class while `Request.formData()` still builds its entries with Node's undici `File`. The route's `audio instanceof File` guard — the same check MEM-004's live-verified route uses on its own `file` field — therefore rejected every valid chunk. Fixed with a `// @vitest-environment node` docblock on that file, reproducing production rather than loosening a production guard to satisfy a test environment. **Any future test of a server route handler that touches `formData()` in this repo needs the same docblock.**
5. **Silent segments burned money and polluted transcripts** — see below.

### The silence finding, and why `MIN_SEGMENT_BYTES` exists

`lib/audioTranscription.ts` originally asserted in a comment that a silent segment "can legitimately transcribe to an empty string... returned as success with empty text." **That is false for genuinely silent audio, and the browser run proved it**: every silence-only segment came back `400 Audio file might be corrupted or unsupported`, surfacing as `api_error`/502.

The measurement explains why. Recorded in Chrome at the component's real settings: **8 seconds of pure digital silence encodes to 110 bytes; 8 seconds of real speech encodes to 32,492 bytes** — 295x. Opus emits no frames for pure silence, so the "audio file" is a bare WebM header with no audio in it at all. OpenAI is right to reject it.

Left alone this was a real product defect, not a cosmetic one: a muted mic or a recorder left running in an empty room would fire one doomed OpenAI call every 8 minutes, **claim a unit of daily budget for each** (the budget is claimed before transcription, correctly, since the chunk looks well-formed), and splice a `[transcription failed for this segment]` marker into the student's actual lecture notes for a stretch where simply nothing was said. Fix: a client-side `MIN_SEGMENT_BYTES = 1024` guard that skips such a segment entirely — not uploaded, not counted, contributes nothing. 1KB is deliberately conservative: at 32kbps even a quarter-second of real audio clears it, and a real microphone's ambient noise floor always produces real frames. The false comment in `lib/audioTranscription.ts` was corrected to state the actual boundary (audio *with* frames but no speech does return empty text and is still a success; audio with *no* frames is rejected upstream and is filtered client-side).

### Post-review fix: a failed final save no longer discards the transcript

The independent merge-evaluation review's strongest note (of an otherwise clean approval): if the "Stop & Save" POST to `/api/documents` fails, the fully-transcribed lecture was gone with no way to recover it — a real, reachable case, not a hypothetical, since `lib/recordingLimits.ts`'s per-user chunk budget (40/day free) is deliberately higher than `/api/documents`'s own per-user upload budget (5/day free, `lib/uploadLimits.ts`) — a free user can legitimately finish transcribing a whole 90-minute lecture (spending real OpenAI calls the whole way) and then have the save itself 429 on a quota it was never checking against until that final request.

**Fix:** `components/lecture-recorder.tsx` now keeps the assembled transcript in state (`pendingSaveText`) rather than only a local variable, on any save failure (non-OK response or network error). The error view renders it back to the user in a dedicated block with a **"Retry save"** button that resubmits the exact same text without re-recording, plus the raw transcript visible to copy manually if preferred. `handleStopAndSave`'s save logic was extracted into a shared `saveTranscript()` used by both the original attempt and the retry, so the two paths can't drift. Starting a brand-new recording (`handleStart()`) explicitly clears any pending unsaved transcript — a deliberate user action, not a silent loss. Not addressed here, and intentionally left as their own follow-up issues per the review's own non-blocking classification: the platform-wide chunk budget being sized in requests rather than audio-minutes (a scripted client could use far more than the 8-minute/1.9MB chunk this feature's own UI produces, since `MAX_CHUNK_BYTES` is sized to the platform ceiling, not the expected size); `app/privacy/page.tsx` not yet disclosing that lecture audio is sent to OpenAI for transcription (the page was already stale pre-dating this feature, but audio capture — third-party voices, jurisdiction-varying consent law — raises the stakes of that gap); and no `MediaRecorder.onerror` handler for a recorder that fails mid-cycle.

## Podcast schema + RLS (MEM-012, real GitHub issue #47, 2026-08-11)

The persistence layer for the AI-podcast feature (a NotebookLM-style Audio Overview), locked with Cynthia on 2026-08-11. **Schema and RLS only** — nothing generates, stores, or serves audio yet; there is no route, no OpenAI call, and therefore no HARD STOP 6 rate-limiting obligation in this ticket. That all belongs to the follow-up generation ticket, which should treat this table as its already-secured storage target.

### The `podcasts` table

One row per generated Audio Overview of a document: `id`, `document_id` (FK→documents, cascade), `user_id` (FK→users, cascade), `status`, `storage_path`, `duration_seconds`, `error_message`, `created_at`.

- **Parent is `documents`, not `notes`.** Locked on issue #47: a podcast is generated from `documents.raw_text`, not from `notes.content`. That decision is what determines which table the RLS parent-ownership check has to point at, so it is a schema fact here, not just a generation-time detail. Structurally `podcasts` is therefore the same shape as `notes` — child of `documents`, `user_id` denormalized — and its policy is `notes_own_rows` with the table names swapped.
- **`status`** (`'pending' | 'generating' | 'ready' | 'failed'`, `NOT NULL DEFAULT 'pending'`) is plain `text`, not a `pgEnum`, following this schema's existing convention for value domains that may still grow. The precedent is real, not theoretical: `documents.source_type` absorbed `'recording'` (issue #42) with zero migration precisely because of this choice. No `CHECK` constraint either, matching `quiz_attempts.score`'s app-level-rather-than-DB-level validation convention.
- **`storage_path`** is a Supabase Storage object path, not a public URL — same convention as `documents.storage_path`. Null until `'ready'`.
- **`duration_seconds`** (integer, nullable) — null until `'ready'`; nothing can derive it before the audio file exists.
- **`error_message`** (text, nullable) — populated on `'failed'` so a future UI can say *why* instead of a bare "something went wrong". `podcasts` is the first async-generation table in this schema (notes/flashcards/quizzes are written synchronously or not at all), so there was no existing failure-state convention to mirror. Deliberately kept minimal: one nullable text column, **no** error-code enum, **no** retry counter, **no** separate errors table. Intended to hold a short internal reason — the same typed-result `reason` strings `lib/*Generation.ts` already produce, e.g. `not_configured` — rather than raw third-party provider output echoed straight back to a user.
- No `UNIQUE` on `document_id`: a document may legitimately have more than one podcast row over time (a failed attempt followed by a successful regeneration). Enforcing one-per-document would make the natural retry path require a delete first, for no benefit this ticket can point at.

### RLS — all five pieces, in one migration, for the first time

`podcasts` is the first new user-data table since MEM-002, so it is the first built against the complete five-piece convention in `CLAUDE.md` rather than acquiring the pieces across `0001`/`0002`/`0003`. Two are drizzle-kit-generated from `lib/db/schema.ts`; **three are hand-written**, because drizzle-kit's pg-core API has no primitive for a `GRANT` or for `FORCE`:

```sql
-- (2) generated from pgPolicy(...)
CREATE POLICY "podcasts_own_rows" ON "podcasts" AS PERMISSIVE FOR ALL
  TO "authenticated", "meminno_rls"
  USING ((select public.meminno_current_user_id()) = user_id)
  WITH CHECK ((select public.meminno_current_user_id()) = user_id
    AND EXISTS (SELECT 1 FROM public.documents d
                WHERE d.id = document_id
                  AND d.user_id = (select public.meminno_current_user_id())));
-- (3)(4)(5) hand-written
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE "podcasts" TO "authenticated";
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE "podcasts" TO "meminno_rls";
ALTER TABLE "podcasts" FORCE ROW LEVEL SECURITY;
```

`USING` stays the flat `user_id = caller` check, deliberately — it already fully scopes what a caller can SELECT / UPDATE-target / DELETE. The `EXISTS` clause is on `WITH CHECK` only, exactly the shape issue #23 established, and is present **from day one** here rather than retrofitted by a later tightening migration: without it, user B could INSERT a podcast row with `user_id = B` while pointing `document_id` at user A's document, since Postgres evaluates FK referential integrity with RLS bypassed by design. `anon` is granted nothing (RLS default-denies it anyway with no policy naming it; withholding the GRANT is a second layer of the same guarantee). `meminno_app` appears in no policy, which combined with `FORCE` is what keeps the migration/owner role unable to read a single podcast row.

### Verification (against the real `hlaeqvuyapkvixwaqxcs` project)

Migration applied for real via `drizzle-kit migrate` as `meminno_app` (`MIGRATION_DATABASE_URL`), then the live catalog was read back directly: `relrowsecurity = true`, `relforcerowsecurity = true`, owner `meminno_app`, exactly one policy (`podcasts_own_rows`, `polcmd = '*'`, roles `{authenticated, meminno_rls}`) whose `WITH CHECK` contains the `documents` `EXISTS` subquery, grants `{authenticated: SIUD, meminno_rls: SIUD}`, and `has_table_privilege('anon', 'public.podcasts', 'SELECT') = false`. Both roles re-confirmed `rolbypassrls = false, rolsuper = false`.

`tests/integration/rls.test.ts` gained a third `describe` block (8 tests, all passing against the live project alongside the pre-existing 10) proving the policy actually enforces something: the five-piece catalog assertions above; an owner inserting and reading back their own row **through the real `withUserContext()` and the real drizzle table object**, not this file's hand-rolled `asUser` helper (worth doing once on a new table — the helper is a faithful copy of `withUserContext`, but a copy, and this is the entry point every future podcast route will actually call); an owner driving the full `pending → ready → failed` lifecycle through real UPDATEs; a second user getting zero rows on cross-user SELECT/UPDATE/DELETE with the row provably untouched afterwards; a session with no identity set seeing nothing; **both directions** of the parent-ownership forgery rejected with a real `row-level security` error (B claiming A's document, and B claiming a row on A's behalf) alongside proof B's own legitimate insert still succeeds; a **forged UPDATE repoint** (B moving their own row's `document_id` onto A's document) likewise rejected, since `WITH CHECK` applies to the post-update row too; and `meminno_app` via `MIGRATION_DATABASE_URL` able to read none of it. All test rows are cleaned up via cascade on the two disposable user UUIDs the suite creates — confirmed afterwards with a post-run `ANALYZE`, `reltuples = 0`.

`tests/unit/schema.test.ts` picked `podcasts` up in its existing `userTables` / `parentChecks` / denormalization / cascade-delete cases, plus one new case pinning the lifecycle contract itself: `status` is `NOT NULL DEFAULT 'pending'` and `storage_path`/`duration_seconds`/`error_message` are all nullable, so a row stays insertable with nothing but its two FKs when generation is queued. A future edit that makes any of the three `NOT NULL`, or that "simplifies" the `withCheck` back to a flat `user_id` check, now fails before it ever reaches a database.

## AI podcast script generation (MEM-013, real GitHub issue #48, 2026-08-11)

The script-generation half of the AI-podcast feature ("Audio Overview," this app's NotebookLM-equivalent core differentiator) — **generation logic only**, no route and no schema change. Text-to-speech synthesis per turn is MEM-014; wiring an actual `POST` route (including this feature's own two-layer rate limiting, per HARD STOP 6) is MEM-015. Do not treat the absence of a route as incomplete — it's this ticket's explicit dispatch scope.

**`lib/podcastScript.ts` — `generatePodcastScriptFromText(sourceText)`.** Architecture mirrored directly from `lib/notesGeneration.ts`/`lib/quizGeneration.ts`, per this ticket's dispatch:
- OpenAI Chat Completions with **forced** tool-use (`tool_choice` pinned to one function, `generate_podcast_script`), returning `{ turns: [{speaker: 'A'|'B', text: string}, ...] }`.
- **`strict: true` OpenAI structured-outputs mode from the start** (`lib/quizGeneration.ts`'s MEM-007-fix pattern, issue #26, applied here proactively rather than after an observed failure) — an array-of-objects-with-required-fields is exactly the shape that failed non-strict forced tool-use for the quiz module in production. Deliberately **no same-ticket retry loop** on top of it, unlike MEM-007-fix: that retry was added to quiz generation only after real evidence of a residual failure rate even with strict mode; with zero production traffic yet for this brand-new module, a preemptive retry would be guessing at a failure mode rather than fixing an observed one.
- The tool-call output is re-validated with zod (`generatedPodcastScriptSchema`) before ever being trusted, persisted, or returned — including two script-level `.refine()` checks beyond the per-turn shape: both speakers must appear at least once (catches the model collapsing to a monologue despite the forced two-value `speaker` enum on every turn), and the script's total word count must fall within a loose `[400, 1600]` sanity band around the prompt's ~750-1050 target (same "schema bound looser than prompt target, exists to catch a broken/abusive response not to police pacing" relationship `lib/flashcardsGeneration.ts`/`lib/quizGeneration.ts` already use).
- Every failure mode is a typed, non-throwing result: `not_configured`, `empty_input` (checked before any API call), `invalid_response` (no tool call, malformed JSON, or a validation failure), `api_error`.
- Input truncated to 60,000 characters before being sent — same `MAX_INPUT_CHARS` bound and cost/latency-predictability reasoning as `lib/notesGeneration.ts`/`lib/quizGeneration.ts`, applied to `documents.raw_text` per this ticket's dispatch instruction to mirror the existing convention rather than invent a new truncation scheme.

**Model: `gpt-5.6-luna`, not `gpt-4o-mini`** (the model every other `lib/*Generation.ts` module uses) — confirmed real, current, and correct for this module specifically per this ticket's dispatch (GA 2026-07-09, OpenAI's newest low-cost tier), and present as a first-class literal in the installed `openai` SDK's own `ChatModel` union type, not merely accepted via its `(string & {})` fallback. Natural multi-speaker conversational writing is the actual product differentiator here and benefits from a newer/stronger model in a way the other three modules' comparatively mechanical structured-extraction tasks don't.

**Real finding from live smoke-testing against the actual OpenAI API, not caught by any mocked test:** `gpt-5.6-luna` is a reasoning-tier model, and OpenAI's `/v1/chat/completions` endpoint outright rejects combining function/tool calling with reasoning enabled — `400 Function tools with reasoning_effort are not supported for gpt-5.6-luna in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'.` Since forced tool-use is this module's whole architecture (and every sibling generation module in this codebase), the fix was `reasoning_effort: 'none'` on the completion call rather than migrating this one module onto the Responses API nothing else here uses. This also keeps latency predictable against `OPENAI_TIMEOUT_MS` — reasoning tokens are billed and add latency this task (structured extraction of a conversation script, not multi-step logical reasoning) doesn't benefit from. A dedicated unit test (`sets reasoning_effort to "none"...`) pins this specifically, since every other mocked test would still pass green even if this param regressed — it doesn't validate request shape against the real API, only this repo's own zod/logic layer.

**Prompt design** (the ticket's explicit "spend real effort here" ask): Speaker A is framed as the prepared host who has read the material and drives the conversation; Speaker B as an engaged co-host who has *not* read it in advance, asks genuine clarifying questions, pushes back, and periodically restates concepts in their own words — a deliberate NotebookLM-style asymmetry chosen because it gives the model a concrete behavioral reason to produce real back-and-forth rather than two names narrating the same monologue in turns. Explicit instructions for backchanneling, genuine reactions/follow-ups, occasional interruptions, sparing verbal fillers, varying turn length, and a hard ban on bracketed stage directions (`[laughs]`, sound cues) — the last one because early iteration risk was the model treating "make it natural" as license to add non-spoken annotations a TTS engine (MEM-014) can't read aloud. Target length (~750-1050 words for a natural 5-7 minute conversation at ~150 words/minute) is stated with the reasoning spelled out in-prompt, plus an explicit "don't pad to hit a word count" instruction, since a schema-only word-count floor without that framing risks the model stuffing filler to clear the bound rather than writing a tighter, better conversation.

**Live smoke-test verification** (real `OPENAI_API_KEY` — this key has been live in Vercel Production and Preview since MEM-008, and is also present in this worktree's local `.env.local`; see `CLAUDE.md`'s Credential-reuse map): one real call against a 4-paragraph cellular-respiration source text produced a genuine 27-turn, 748-word two-speaker script with real clarifying questions ("Wait, since glycolysis makes two pyruvate, does the Krebs cycle run once or twice?"), a running-recap turn near the end, correct-and-complete coverage of the source material's actual numbers (2 ATP/2 NADH from glycolysis, 32-34 ATP from oxidative phosphorylation, ~36-38 ATP total), and zero bracketed stage directions — output judged genuinely usable, not just schema-valid. This was a one-off manual verification via a disposable script, deleted afterward per `CLAUDE.md` HARD STOP 2 (never committed).

## Affiliate/referral attribution (MEM-018, real GitHub issue #52, 2026-08-11)

Growth channel #2, locked with Cynthia on a real call the same day: a small-creator affiliate program, >50% revenue share per converted signup, no upfront pay. This ticket is deliberately the minimum viable slice — **attribution tracking only**, no payout automation. Pranav calculates and pays revenue share manually off a query against `users.referredByCode` joined to subscription status for now; a real `promo_codes` table, self-serve code management, an admin UI, or any discount to the referred user are all explicitly out of scope until there are enough affiliates to justify them.

**Two independent capture paths, one shared column.** The original scope was link-only (`?ref=<code>`), but a mid-implementation correction from the actual Cynthia call transcript widened it: creators may say a code out loud in a video ("use code CYNTHIA") rather than relying on a clickable bio link, especially on platforms like TikTok where link placement is more limited than a standard bio-link surface. Both paths write the same `meminno_ref` cookie and feed the same `users.referredByCode` column through the same first-insert-only logic in `lib/session.ts`:

1. **`?ref=<code>` on the marketing landing page** (`proxy.ts`) — the bio-link-click path. `app/page.tsx` is a Server Component, and Server Components can read cookies but cannot write them (see `proxy.ts`'s own pre-existing header comment on why the Supabase session-refresh logic already lives in the proxy rather than in `lib/supabase/server.ts` alone) — so this is the one place in the App Router that reliably can, on every request. Scoped specifically to `pathname === '/'` (not every route) so an unrelated `ref` query param elsewhere in the app can never accidentally re-attribute a signup. Reads the final `response` object (not one captured before the Supabase `getUser()` call above it), since that call's own `setAll` callback may have reassigned `response` to a fresh one carrying refreshed auth cookies — writing onto a stale reference would have silently dropped the referral cookie.
2. **An optional "Referral code" text field on `/sign-in`** (`app/sign-in/actions.ts`'s `setReferralCookie` server action) — the spoken-code path. Called directly as a plain async function from the client-side submit handler in `app/sign-in/page.tsx` (a Server Action invoked without a `<form action={...}>`, which Next.js supports identically to the form-bound style already used elsewhere in this app), *before* `signInWithOtp()` fires, so the cookie's `Set-Cookie` has already landed in the browser by the time the user later clicks the magic-link email and lands on `app/auth/callback/route.ts` — the same "same browser" requirement the magic-link PKCE flow itself already has. Best-effort: a failure here is swallowed rather than blocking sign-in, since attribution is strictly secondary to the user being able to sign in at all.

Both write paths and their shared config/normalization live in **`lib/referral.ts`**: `REFERRAL_COOKIE_NAME` (`meminno_ref`), `REFERRAL_COOKIE_MAX_AGE_SECONDS` (30 days — long enough to cover a realistic browse-then-signup gap for a college-student audience, short enough that a years-stale cookie doesn't misattribute an unrelated later signup), `REFERRAL_COOKIE_OPTIONS` (`httpOnly: true` — nothing client-side ever needs to read this cookie's value, since even the manual-entry path sets it via a server action rather than `document.cookie` — `sameSite: 'lax'`, `secure` in production, `path: '/'`), and `normalizeReferralCode()` (trims whitespace, returns `null` for empty/blank/absent input; no case-folding or format validation beyond that, since issue #52 validates a code only by non-emptiness).

**First-touch, not last-touch, with an explicit-override exception — and this is where the real correctness risk was per the ticket brief.** `lib/session.ts`'s `ensureUserRow()` (called from `getSessionUser()` on every session resolution, per its pre-existing MEM-003 design) now reads the `meminno_ref` cookie via `next/headers`'s `cookies()` on every call, but the column only ever actually changes on a row's true first `INSERT`:

```ts
const [profile] = await withUserContext(userId, (tx) =>
  tx.insert(users)
    .values({ id: userId, email, ...(referredByCode ? { referredByCode } : {}) })
    .onConflictDoUpdate({ target: users.id, set: { email } })
    .returning({ plan: users.plan })
)
```

`referredByCode` is included in `values` (the insert branch) but deliberately absent from `onConflictDoUpdate`'s `set` (the update branch), which stays exactly `{ email }` — unchanged from MEM-004's original design. That is what enforces "set once at signup, never overwritten after" at the SQL level, not application logic that could drift: on a conflict, Postgres runs `SET email = excluded.email` and nothing else, so a stale or different `meminno_ref` cookie on the 2nd/3rd/Nth call for an already-existing user is provably inert — `tests/unit/session.test.ts`'s new `describe('MEM-018: referredByCode ...')` block calls `getSessionUser()` three times in a row for the same existing user with a cookie present the whole time and asserts `onConflictDoUpdate`'s `set` argument never contains the key on any of the three calls, plus the four other new tests covering the insert-time behavior (cookie present → included, cookie absent → omitted, blank/whitespace cookie → omitted). The "first-touch vs. explicit-override" nuance lives one layer up, in the two write paths themselves, not here: neither `proxy.ts` nor `setReferralCookie` ever clears the cookie on an empty/absent value (so a plain revisit or a blank-field sign-in never wipes out an existing attribution), but both unconditionally overwrite it whenever a NEW non-empty code is explicitly supplied (a legitimate re-attribution signal — e.g. clicking a different creator's link, or typing a different code in) — by the time `ensureUserRow()` ever reads the cookie, whatever value is there already reflects that policy correctly.

**No RLS/GRANT changes needed.** `referredByCode` is a plain nullable column on the existing `users` table, added via a single-statement migration (`drizzle/0005_mem-018-affiliate-referral-tracking.sql` — originally generated/applied as `0004`, renumbered after a collision with MEM-012's own independently-generated `0004`; see the "Migrations" section above for the full renumbering note). RLS is row-level, not column-level, and the existing `users_own_row` policy (`FOR ALL TO authenticated, meminno_rls`, scoped by `id`) and existing table-level `authenticated`/`meminno_rls` grants already cover every column on the row, this one included — verified by reading the current policy in `lib/db/schema.ts` before assuming so, per this ticket's own dispatch instructions, rather than adding redundant GRANT statements that would have been a no-op.

**Tests:** `tests/unit/referral.test.ts` (pure `normalizeReferralCode()`/config unit tests), `tests/unit/proxy.test.ts` (new file — `proxy()` previously had no test coverage at all; the Supabase session-refresh half is mocked out since it's a real network call already covered by other tickets' live verification, these 5 tests are specifically about the MEM-018 referral-cookie addition: set-on-`ref`-present, not-set-on-no-`ref`, not-set-on-blank-`ref`, overwrite-on-new-explicit-`ref`, and scoped-to-`/`-only), `tests/unit/sign-in-actions.test.ts` (new file, mirrors `tests/unit/billing-actions.test.ts`'s `next/headers` mocking approach for `app/sign-in/actions.ts`'s own server action), and the `describe('MEM-018: ...')` block added to the existing `tests/unit/session.test.ts` described above. Migration applied directly against the live `hlaeqvuyapkvixwaqxcs` project via `drizzle-kit migrate` (`meminno_app`/`MIGRATION_DATABASE_URL`) and confirmed via a disposable, not-committed verification script against `information_schema.columns` (per HARD STOP 2) — no `tests/integration/` change, since this ticket adds no new RLS-scoped table and the existing `rls.test.ts` suite already exercises the `users` table's policy end to end.

## Podcast audio + Supabase Storage (MEM-014, real GitHub issue #49, 2026-08-11)

The audio half of the AI-podcast feature: turn MEM-013's speaker-tagged script into a real, playable file, put it somewhere, and hand out access to it safely. Two firsts for this codebase — **the first billed vendor other than OpenAI (Google), and the first Supabase Storage integration of any kind.** MEM-015 wires these into a route; MEM-016 builds the player.

### `lib/podcastAudio.ts` — Gemini multi-speaker TTS

Everything below was checked against real API calls made during this ticket, not against a doc page.

- **Model: `gemini-2.5-flash-preview-tts`.** Confirmed live by listing `GET /v1beta/models` with this project's own key — it is real, current, and its `supportedGenerationMethods` includes `generateContent`. Two siblings are also live (`gemini-2.5-pro-preview-tts`, `gemini-3.1-flash-tts-preview`), and `gemini-3.1-flash-tts-preview` was separately live-tested to accept this exact multi-speaker config unchanged, so switching is a one-constant edit. This one is chosen because it is **2x cheaper on both sides of the meter** ($0.50/1M text in + $10.00/1M audio out, vs $1/$20 for both others) and cost is the entire point of HARD STOP 6. All three are preview-tier; re-verify against a live listing if calls start 404ing.
- **Voices: `Kore` and `Puck`**, two real names from Gemini's documented 30-voice set and the pair its own multi-speaker example uses. Chosen for separability — with no visual cue, a listener has to be able to tell the speakers apart.
- **Speaker labels are read out of the script, not hardcoded.** The module takes the distinct `speaker` values in order of first appearance and maps them to the two voices, so it does not care whether MEM-013 emits `A`/`B` or `Alex`/`Sam`. Gemini's own SDK type says multi-speaker takes **exactly two** speakers; a script with one or three is rejected rather than silently trimmed.
- **Bracketed stage directions are stripped defensively before synthesis** (`stripStageDirections()`). MEM-013 is prompted not to emit `[laughs]`/`[pause]` and did not in its reviewer's real runs, but that is a prompt instruction rather than a guarantee, and this model has no expressive-tag feature — a stray direction is simply **read aloud** in a finished podcast. Stripping at the last point before the API call makes it hold whatever produced the script. A turn that was nothing but a direction is dropped rather than sent as a bare `Alex:` line.
- **That strip is deliberately narrow, and the bias is toward stripping too little.** MEM-014's review caught that the original naive `\[.*?\]` turns "the array `a[0]`" into "the array a" — which in a **study app** means silently corrupting real course material, a far worse outcome than one stray `[laughs]` being spoken. A span now only counts as a direction if it starts at a whitespace boundary (ruling out every `a[0]`/`x[i]`/`arr[idx]` form, which attach directly to an identifier), its first token is 3+ letters (ruling out "the value [i]"), and it contains only letters, spaces, apostrophes and hyphens (ruling out `[0]` and `[n+1]`). An unclosed `[` is left alone too. Five regression cases pin exactly this.
- **`invalid_script` is its own failure reason**, separate from `empty_input` — also from the review. Empty input means there was nothing to say; `invalid_script` means there was content whose shape is unusable (not exactly two speakers). Different failures with different fixes — the first is a user-facing empty state, the second an upstream generation bug — so MEM-015 can route and log them apart rather than inferring intent from one overloaded discriminator.
- **The turn type is `PodcastAudioTurn`, not `PodcastScriptTurn`.** MEM-013 merged while this branch was open and exports its own `PodcastScriptTurn`; renaming this one avoids a collision so MEM-015 can import from both modules without an alias. It stays a locally-declared `{ speaker: string; text: string }` rather than an import, because this module genuinely does not care about labels and should not be coupled to MEM-013's `'A' | 'B'` literal union — and MEM-013's type is assignable to it anyway, so `generatePodcastAudio(script.turns)` type-checks with no adapter.
- **The response is RAW PCM, and that is the trap in this ticket.** Gemini returns base64 samples with no container. Storing those bytes as `.wav` (or feeding them to `<audio>`) produces a file every player refuses, because nothing tells it the sample rate, channel count, or bit depth. `wrapPcmInWavContainer()` prepends a canonical 44-byte RIFF/WAVE header. **Verified with macOS CoreAudio** (`afinfo`) on a real 4.63-minute synthesis: `File type ID: WAVE, 1 ch, 24000 Hz, Int16, estimated duration 277.57 sec`. The header is pinned field-by-field in `tests/unit/podcastAudio.test.ts`.
- **The announcing mimeType is not consistent between models**, so it is parsed tolerantly rather than string-matched. Both of these are verbatim from real responses this ticket captured: `audio/L16;codec=pcm;rate=24000` (2.5) and `audio/l16; rate=24000; channels=1` (3.1) — different casing, spacing, and fields.
- **WAV, not MP3/AAC**, because it is the only format reachable without adding a native audio encoder to this project, and it plays natively in every browser. The cost is size: ~2.9MB per minute, so a 7-minute podcast is a ~20MB object. Compressing it is a real follow-up, not a blocker.
- **`retryOptions: { attempts: 1 }` is load-bearing.** The `@google/genai` SDK retries **five** times by default (its own `HttpRetryOptions` doc: "If not specified, default to 5"). On a call that can run four minutes that is a 20-minute worst case, with every attempt that reaches the model billed as audio output. One attempt only.

### Latency, cost, and what MEM-015 has to do about it

Measured on a real synthesis of a genuine 831-word two-speaker script:

| | measured |
|---|---|
| audio produced | 4.63 min (277.6s) |
| wall clock | **144s** (~31s per minute of finished audio) |
| tokens | 1,207 text in + 6,939 audio out |
| **cost** | **$0.070** |

**This is a multi-minute request, and MEM-015 must design for that.** The route needs an explicit `maxDuration` of at least 300 — not the 60/120 the other AI routes use — and the whole pipeline is two billed calls (script + TTS) that should claim the budget **once**, before the script call. `MAX_SCRIPT_CHARS = 7_000` bounds a synthesis to roughly 6.2 minutes / ~195s, inside MEM-013's 5-7 minute target and under the module's 240s per-attempt timeout. It is nowhere near the model's 8k-token input ceiling — latency and cost are what that bound exists for, not context. If podcasts ever need to be longer, the honest answer is a background job, not a bigger timeout.

### Supabase Storage — the design, since nothing existed to copy

- **Bucket `podcasts`, private**, created once by `scripts/setup-podcast-storage.mjs` (`node --env-file=.env.local scripts/setup-podcast-storage.mjs`), idempotent and safe to re-run. **Already run against the live `hlaeqvuyapkvixwaqxcs` project** during this ticket. Explicit setup rather than a lazy `createBucket()` on first upload, for the same reason CLAUDE.md's SQL role bootstrap is a documented one-time block: infrastructure that exists exactly once should be a reviewable action, not a side effect in a request path that would then need bucket-creation privileges on every call and could half-apply under concurrency. `allowedMimeTypes: ['audio/wav']`, `fileSizeLimit: 50MB`.
- **Path `podcasts/{userId}/{podcastId}.wav`** — the ticket's convention read literally: bucket `podcasts`, object path `{userId}/{podcastId}.wav` inside it, which is exactly how Supabase addresses it. No redundant second `podcasts/` prefix. `podcasts.storagePath` (MEM-012's column) holds the in-bucket path, because that is the string `createSignedUrl()` takes. The `{userId}` segment is not an access control — it exists so a user's objects can be listed or deleted as a unit for account deletion without a DB round trip. Both ids are UUID-validated before interpolation, so nothing resembling `../` can reach a storage key.
- **No `storage.objects` RLS policies on this bucket — a decision, not an omission.** A private bucket with no policies is default-deny for `anon`/`authenticated`: a browser holding a real user JWT can neither list nor download from it. Uploads and signing run server-side under `SUPABASE_SERVICE_ROLE_KEY`, which bypasses bucket policies anyway, so a policy written today would have exactly zero effect on the only code path that exists. **The real boundary is: a caller obtains a signed URL only by asking our server, and the server mints one only after reading the `podcasts` row through `withUserContext()`, where MEM-012's FORCE'd policy has already proven ownership.** The DB row is the gate; the signed URL is the capability it issues. **What would invalidate this:** any future ticket giving the browser direct Storage access (a client-side upload, a `supabase.storage.from('podcasts')` call in a component) makes object-level RLS mandatory in that same PR, because the service-role-only assumption stops holding.
- **Signed URLs expire in 1 hour.** A 5-7 minute podcast has to survive a full listening session, and `<audio>` re-issues range requests on every seek and replay, so an expiry in minutes would break scrubbing back through a lecture. It stays short because the URL is a bearer capability — anyone who obtains it can fetch until it expires, with no further auth check. MEM-015/016 should mint a fresh URL per page load rather than persisting one.
- `lib/podcastStorage.ts` builds its service-role client **per call, inline**, never at module scope, so an unset key fails closed instead of throwing at import — the same shape `lib/audioTranscription.ts` uses. It is not `lib/supabase/server.ts` (the cookie-bound anon client, which by design cannot write a private bucket), and it never touches user tables, so it cannot be used to sidestep the RLS the rest of the app relies on.

### `lib/podcastLimits.ts` — caps sized from measured cost, not copied

HARD STOP 6's two layers, same shape as `lib/notesLimits.ts`, own `podcast-generation` Redis namespace, `meminno-` prefixed. The numbers are deliberately unlike every other feature's because **one podcast costs ~$0.10, roughly sixty times one notes/flashcards/quiz generation.**

- **2/day free** (not 5): at ~$0.10 a call, the usual 5/day would be $0.50/day of vendor spend per free account for the most expensive thing the product does. Two is still enough to genuinely try the feature.
- **5/day paid** (not 50), derived from unit economics: $17.99/month is ~$0.60/day of revenue, and 5 × $0.10 = $0.50/day, so **a subscriber who maxes this out every single day of the month still costs less than they pay** ($15 vs $17.99; the semester plan works out the same daily). A 50/day cap would be ~8x that subscriber's revenue — a ceiling that inverts the business model is not a sanity ceiling. Five is also well above realistic use.
- **50/day platform-wide**: ~$5/day absolute worst case, the same daily dollar ceiling `lib/notesLimits.ts` sized its 300/day against — the call count is 6x lower only because each call costs ~60x more. The Propinno incident behind this hard stop burned ~$17/day, so this bounds the equivalent blast radius ~3.5x tighter. It is deliberately the binding constraint at current scale (25 free users or 10 subscribers at their personal max); real demand hitting it is a signal to raise it with usage data, not evidence it was wrong to start here.

### Known limitations and follow-ups, disclosed rather than hidden

- **WAV is uncompressed** — ~20MB for a 7-minute podcast. Fine for Storage and a signed-URL download, but transcoding to MP3/AAC would cut egress and storage ~10x. Deferred because it needs an encoder dependency this project does not have.
- **No route, no schema, no UI here.** The `podcasts` table landed separately in MEM-012 (merged while this branch was open, hence the `ARCHITECTURE.md` merge); the route is MEM-015. Nothing in this PR reads or writes a table, so none of CLAUDE.md's five RLS obligations apply to it — MEM-012 already discharged them for `podcasts`.

- **`GEMINI_API_KEY` is set in Vercel Production** (by Pranav directly) and locally. It is **not** set in Vercel Preview, so podcast generation on a preview deploy will take the `not_configured` fail-closed path until someone adds it.

## Podcast generation route (MEM-015, real GitHub issue #50, 2026-08-11)

The ticket that turns MEM-012 (schema) + MEM-013 (script) + MEM-014 (TTS/Storage/budget) into one user-visible action. Everything below lives in a single new file, `app/api/documents/[id]/podcast/route.ts`; no schema change, no new `lib/` module, no UI (that is MEM-016).

### Route shape

| | `POST /api/documents/[id]/podcast` | `GET /api/documents/[id]/podcast` |
|---|---|---|
| body | none | — |
| 200 | `{ podcast, audioUrl, expiresInSeconds, existing: true }` — a ready podcast already existed | `{ podcast, audioUrl, expiresInSeconds }` |
| 201 | `{ podcast, audioUrl, expiresInSeconds }` — freshly generated | — |
| 400 | malformed document id (before the session is even resolved) | same |
| 401 | no valid session | same |
| 404 | document missing or not the caller's | no podcast for this document (or the document isn't the caller's) |
| 409 | a generation for this document is already in flight | — |
| 422 | document has no text; or a model returned something unusable | — |
| 429 | burst-limited, or the daily/platform podcast budget is spent | — |
| 502 | OpenAI/Gemini/Storage upstream failure | — |
| 503 | `OPENAI_API_KEY`/`GEMINI_API_KEY`/service-role credentials unset | — |

`podcast` is an explicit allow-list of `{ id, documentId, userId, status, durationSeconds, errorMessage, createdAt }`. **`storagePath` is deliberately never in a response** — it is an internal Storage key, and the only sanctioned way to fetch audio is a signed URL this server mints after proving ownership. An allow-list rather than an omit-one-key spread, so a column added to `podcasts` later has to be opted into the API surface rather than appearing in it by default.

`audioUrl` is minted fresh on **every** response and persisted nowhere, per MEM-014's signed-URL note: the URL is a one-hour bearer capability, `podcasts.storage_path` is the durable thing. It is `null` whenever the row isn't `ready` — and also if signing itself fails on an otherwise-successful generation, which still returns **201**: the podcast genuinely exists and has been paid for, so failing the whole request over a signing hiccup would be dishonest when the client can just re-ask via `GET`.

### Ordering: burst → validate → claim, once

Unchanged from MEM-004's merge-review lesson and pinned by `lib/podcastLimits.ts`'s own header: burst check first (cheap, document-independent), then everything that can 404/409/422, and only then `claimPodcastBudget()`. Both budget calls increment a Redis counter unconditionally, so a request that was never going to generate must not reach them. Tests cover each of those exits asserting `claimPodcastBudget` was not called.

**The budget is claimed exactly once for the whole pipeline**, before the script call — not once per billed vendor call. Generating a podcast is two billed calls (OpenAI for the script, Google for the TTS) but one user-visible action costing ~$0.10 end to end; claiming twice would silently make the documented 2/day free cap mean 1/day.

### A row is written before generation, not after

Every other generation route in this repo inserts only on success, because they either succeed or leave nothing behind. This one spends minutes and real money first, so the `podcasts` row is inserted **before** the script call with `status: 'generating'` and updated on every terminal outcome — `'ready'` + `storagePath` + `durationSeconds`, or `'failed'` + `errorMessage`. That is exactly what MEM-012 added `status`/`error_message` for, and it is what lets a caller (and MEM-016) tell "this failed, here's why" apart from "nothing was ever started."

- `'generating'`, not `'pending'`, on insert: nothing queues this — the row is created by the request already working on it. `'pending'` is left meaning "queued, nobody has started" for a future background-job version.
- `error_message` gets the short internal `reason` string (`api_error`, `not_configured`, …), never raw vendor text echoed back to a user — MEM-012's schema comment specifies that column exactly this way.
- The failure-marking update is wrapped so it **cannot** throw: the request is already failing, and losing the real user-facing error to a secondary DB error would be strictly worse than a row stuck at `'generating'`. Covered by a test that makes that specific `withUserContext` call reject and asserts the caller still gets the mapped 502.

### Existing-podcast handling — the judgment call (issue #50 doesn't specify it)

Only the **newest** row for the document is consulted, which makes the cases mutually exclusive:

- **`ready` → returned as-is, 200, `existing: true`. Not regenerated, no budget claimed, no vendor call.** A podcast costs ~60x a notes/flashcards/quiz generation against a 2/day free cap, so silently burning a user's whole day's allowance to re-make something they already have is the wrong default. This is a real divergence from the notes/flashcards/quiz routes, where each POST deliberately creates a new row — there, a second take is cheap and often what you want; here there is no cheap second take. An explicit `?regenerate=true` is the right way to add one, when a UI actually asks for it.
- **`pending`/`generating` younger than `STALE_GENERATING_MS` (10 min) → 409, in flight.** Generation is synchronous, so a second concurrent request would spend a second budget unit and a second ~$0.10 producing a duplicate of what the first request is already producing — the exact double-charge a mashed button causes. The burst limiter narrows that window but does not close it (it allows several requests inside its window, and this one runs for minutes).
- **`pending`/`generating` older than that → marked `failed` with `error_message: 'timed_out'`, and the request regenerates.** See below — this is the recovery path, not a heuristic.
- **`failed` → not a blocker.** A retry generates for real and creates a new row; the failed row stays as the record of what went wrong.

#### Stranded-row recovery — why the staleness cutoff is provable, not a guess

A function killed at the `maxDuration` ceiling runs *nothing* afterwards, so the row it left at `'generating'` is never marked failed. Without a recovery path that **permanently bricks the document**: the budget unit is already spent, every later POST 409s forever, every GET leaves MEM-016's poller spinning forever, and the only repair is a manual DB `UPDATE` this repo has no admin tooling for. On the free plan (2/day) that costs half a day's allowance *and* renders the document permanently un-podcastable, whose only user-side workaround — delete and re-upload — cascades away that document's notes/flashcards/quizzes too. This route's own worst-case math makes it a live risk rather than an exotic one: ~250s normal, ~295s pathological, hard kill at 300s, against a preview-tier Gemini model with no latency SLA.

The cutoff needs no field data to size, which is why the original "don't guess without a real occurrence" framing was wrong: `maxDuration = 300` is a **hard, confirmed platform ceiling** (Vercel Hobby/Fluid Compute), and generation is synchronous, so *no* live request can still be working on a row past 300s. Anything older is provably dead. `STALE_GENERATING_MS = 10 min` is 2x that ceiling — slack for clock skew between the DB's `now()` and the function's clock, plus pre-handler queueing. Recovery happens inline on the next POST, so no sweeper, cron, or background job is needed. `'timed_out'` is deliberately a distinct `error_message` from the generation modules' own typed reasons: this row did not fail a vendor call, it was killed mid-flight, and that is worth telling apart in the data.

#### Two "row vanished" guards on the same path

`podcasts.document_id` is `ON DELETE CASCADE`, so deleting the source document during the ~250s generation window takes the podcast row with it and the final `UPDATE ... RETURNING` matches zero rows. Dereferencing that `undefined` would be an unhandled 500 with no log line, so it returns a clean **409** plus a loud `logger.error` naming the now-orphaned Storage object (the audio is uploaded and paid for either way — an orphan-cleanup pass belongs with the account-deletion flow MEM-014 already flagged as missing). The `INSERT ... RETURNING` one line earlier gets the same guard mapped to a 500; that one should be unreachable, but it was free to add in the same pass.

### `maxDuration = 300`, and why there is no more margin to give

Worst case, entirely from MEM-013/MEM-014's real measurements: script gen `(OPENAI_MAX_RETRIES + 1) × OPENAI_TIMEOUT_MS` = 2 × 20s = **40s**, TTS one attempt bounded by `MAX_SCRIPT_CHARS = 7,000` at a measured ~28ms/char ≈ **195s**, a ~20MB uncompressed WAV upload ≈ **10s**, plus session/burst/lookup/insert/two updates/signing ≈ **5s** — about **250s**, leaving ~50s of margin at 300.

That is not a comfortable margin, and the reason it isn't bigger is a hard platform limit rather than a choice: Vercel's Fluid Compute Hobby ceiling is 300s (see the issue #24 section above), and declaring more than the plan allows fails the deployment outright. The pathological case — Gemini burning its full 240s `GEMINI_TIMEOUT_MS` rather than finishing in ~195s — comes to ~295s and would be killed by the platform at 300 either way. **`MAX_SCRIPT_CHARS` must not be raised without first moving this off a synchronous request**, which is the same conclusion MEM-014's entry reached independently: the honest fix for longer podcasts is a background job, not a bigger timeout. `maxDuration: 300` was confirmed in the build's own `functions-config-manifest.json`, not just in source, per issue #24's verification discipline.

### Why `GET` is in this ticket rather than deferred to MEM-016

MEM-016 (the player) has to poll status while a generation runs and needs a playable URL on every page load, and signed URLs expire in an hour and are deliberately never persisted — so "give me a fresh one" is a permanent requirement of the feature, not a convenience. The only alternative would be re-POSTing, which is mutating and budget-touching. It is deliberately tiny: same 400/401 gates, same `withUserContext` + explicit `user_id` filter, and 404 collapses "no such document", "not your document", and "no podcast yet" into one indistinguishable response.

**No rate limiting on `GET`, deliberately.** HARD STOP 6 covers endpoints that call a billed vendor; this one is a DB read plus a signed-URL mint, makes no billed call, and is expected to be polled. It is a read endpoint in the same class as `app/api/me`, which likewise has none.

### Known limitations, disclosed rather than hidden

- **Generation is synchronous.** A caller holds a request open for up to five minutes, and a client that navigates away mid-generation loses the response (the row still completes and is retrievable via `GET`, which is much of why `GET` exists). Everything about this route is sized to that constraint; a background job is the real fix if podcasts ever need to be longer.
- **The 409 in-flight guard is a check, not a lock, and its race window is ~100-300ms** — not "milliseconds": a second request has to clear session resolution, the burst check, and the document lookup before the first request's INSERT lands, and either can win. Worst case is one duplicate podcast and one extra budget unit, which HARD STOP 6's caps already bound financially, so a DB-level unique/advisory lock was judged disproportionate. **MEM-016 should not under-weight this**: client-side disable-on-submit is the intended mitigation, and at ~100-300ms a double-click genuinely can produce two requests.
- **A `'generating'` row orphaned by a killed function no longer bricks the document** (see "Stranded-row recovery" above), but recovery is inline on the next POST — nothing reclaims the spent budget unit, and the Storage object from a run that uploaded before dying is not cleaned up. Both belong with the account-deletion/orphan-sweep flow MEM-014 already flagged as missing.
- **`GEMINI_API_KEY` is not set in Vercel Preview** (MEM-014's note), so this route takes the `not_configured` → 503 path on preview deploys until someone adds it. Production has it.

## Podcast player (MEM-016, real GitHub issue #51, 2026-08-12)

The frontend for MEM-015's route — the last ticket in the podcast feature (MEM-012 through MEM-015 are all merged). One new component, `components/podcast-section.tsx`, rendered unconditionally at the bottom of `components/document-workspace.tsx` (unlike flashcards/quizzes, a podcast never needs a note to exist first — MEM-015 generates straight from `documents.raw_text`, the same source `generateNotes()` reads).

### Why its own component instead of folding into `document-workspace.tsx`

Every other generation button in that file is a single request/response cycle: POST, get a result or an error, done. Podcasts are a genuinely different shape — the POST itself can run for up to route.ts's `maxDuration = 300`, can come back `409` if a previous request (this tab, another tab, or one stranded from before a reload) is already working, and has to resume tracking that in-flight state via polling on a fresh page load rather than only right after a click. That state machine and its tests are large enough, and different enough, that keeping them separate from `document-workspace.tsx`'s simpler flows keeps both readable.

### State machine

`checking` (mount-time `GET`) → `none` | `ready` | `failed` | `polling` (an in-flight row found on load), then from `none`: `submitting` (the click-to-`POST`) → `ready` | `failed` | `polling` (a `409`), and `polling` → `ready` | `failed` | `timeout`. `failed` and `timeout` both offer a button back into the flow (`Try again` re-`POST`s; `Check status` re-`GET`s, escalating to a real `POST` if the row is still stuck — see the post-review fix below).

- **Disable-on-submit, per route.ts's own flagged risk.** The route's header comment measures the check-to-insert race window at ~100-300ms — long enough for a real double-click to file two `POST`s. `handleGenerate` guards with a `useRef` boolean checked and set *synchronously*, before the `setState` that disables the button even renders, so two click events fired in the same tick can't both pass it; the state-driven `disabled` prop is the second, UI-visible layer on top of that.
- **Mount check picks up an existing podcast without a click** (item 4 of the ticket brief): `ready` renders the player immediately, `failed` renders the retry state, `generating`/`pending` starts polling from where a previous request (this session or another) left off. A transient network error on this one check is treated the same as `none` — deliberately, not a bug: the very next click on "Generate podcast" would hit route.ts's own `409` in-flight check and recover into polling from there if something really was running, so failing softly here doesn't risk masking a real generation.
- **Polling: 4s interval, 330s ceiling.** 4s sits in the middle of the ticket's suggested 3-5s range. The 330s ceiling is route.ts's own `maxDuration = 300` (a hard, confirmed Vercel Fluid Compute platform ceiling per that file's header comment — no live request can still be working past it) plus 30s of margin for this poller's own network latency and the gap between the `POST` that started generation and this component's first tick, so a generation finishing right at the server's own deadline isn't cut off by a client timeout tighter than the server's own. Exceeding it without a terminal status stops polling and shows a "taking longer than expected" state with a `Check status` button, rather than spinning forever past the point generation could possibly still be running.
- **Error messages match the actual failure, not a generic string**, per the ticket's explicit requirement. Two different sources needed two different handling paths: a `POST` failure (422/429/502/503) always carries route.ts's own specific, human-readable `error` string (e.g. "Free plan is limited to 2 podcasts per day. Upgrade for a higher daily limit."), used verbatim; a podcast discovered already-`failed` via `GET` (mount check or a poll landing on a terminal row) only carries the short internal `errorMessage` reason code (route.ts's `publicPodcast` allow-list never includes the friendly `message` string outside a `POST` response body), so a local `REASON_MESSAGES` map translates each of route.ts's seven typed reasons (plus `'timed_out'`, MEM-015's own stranded-row-recovery marker) into the same kind of specific, honest sentence rather than a bare code.
- **`ready` with no `audioUrl`** (MEM-015's own documented edge case: generation can succeed at 201 with signing itself failing) gets its own small recovery affordance — a "Reload player" button that re-`GET`s for a fresh signed URL — rather than being treated as a failure the podcast wasn't.
- **No regenerate button on `ready`.** Unlike notes/flashcards/quizzes, a second `POST` against an already-`ready` podcast doesn't create anything new — route.ts returns the same existing row (200, `existing: true`, no budget spent) by design, since a podcast costs ~60x a text generation against a 2/day free cap. Showing a "Regenerate" action that silently does nothing would be dishonest, so the header button is simply absent once `ready`.

**Post-review fix, not in the original dispatch: `timeout`'s "Check status" now escalates to a real `POST` when its recheck `GET` still finds the row stuck.** The independent review caught a genuine closed loop: route.ts's stranded-row recovery (`STALE_GENERATING_MS`) only runs inside its `POST` handler — `GET` never mutates anything. `handleCheckAgain` originally only ever called `GET`, so on a truly stranded row (the exact scenario `STALE_GENERATING_MS` exists to recover) it could only ever re-report `'generating'` forever: no `POST` reachable from `timeout` at all, the document permanently un-podcastable, and the spent daily budget unit never reclaimed. The reviewer proved this empirically before proposing the fix — a permanently-`'generating'` row, three simulated "Check status" cycles across ~17 minutes, zero `POST`s fired. Fixed by making `handleCheckAgain` fall through to `handleGenerate()` (a real `POST`) when its own quick recheck `GET` still reports in-progress: cheap and correct in the common case (the podcast actually finished right around the client's own deadline, no `POST` needed), and the only thing that can actually recover a genuinely stranded row otherwise. The escalation `POST` is itself safe either way it lands — a harmless `409` if the row turns out to still be within its 10-minute server-side grace window (resumes polling from there), or route.ts's real recovery-and-regenerate path if past it. Pinned by two new tests: one asserting the exact call sequence (`GET` then `POST`, not `GET` then `GET`) when the recheck still finds the row stuck, one covering the harmless-409-resumes-polling sub-case.

**Two smaller non-blocking findings from the same review, folded into this pass:**
- **The two different `409` shapes route.ts can return were previously treated identically.** `POST`'s "already in flight" `409` carries a `podcast` field; its separate "document changed or removed mid-generation" `409` (the `podcasts.document_id` `ON DELETE CASCADE` case from route.ts's own "row vanished" guard) does not, and is a genuine terminal failure with nothing left to poll for. `handleGenerate` now branches on whether `body.podcast` is present — with it, start/resume polling as before; without it, show the real failure message via the `failed` state instead of silently treating it as "still generating" and then degrading to "No podcast yet" once the next poll 404'd.
- **The original unmount test didn't actually prove interval cleanup** — it would still have passed even with a leaked interval, since nothing advanced fake time past the unmount point. A second test now unmounts, then advances several poll intervals' worth of fake time, and asserts zero additional `fetch` calls occurred — a direct proof that `stopPolling()` in the mount effect's cleanup actually clears the interval, not just that `mountedRef` happens to swallow a stray late state update.
